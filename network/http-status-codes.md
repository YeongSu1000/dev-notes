## HTTP 상태 코드

> HTTP 응답 상태 코드는 특정 HTTP 요청의 처리 결과를 나타냅니다. **응답은 5개의 그룹으로 나누어집니다**: 정보를 제공하는 응답, 성공적인 응답, 리다이렉트, 클라이언트 에러, 그리고 서버 에러. 상태 코드는 [section 10 of RFC 2616](https://datatracker.ietf.org/doc/html/rfc2616#section-10)에 정의되어 있습니다.

- **상태 코드가 왜 필요한가?**
  - 상태 코드는 서버가 클라이언트의 Request를 처리한 뒤 **요청이 어떻게 됐는지**를 알려주는 정보다.
  - 아래에서 서버의 처리 결과를 나타내는 숫자가 상태 코드다.
  - ```text
    Request
    │
    │ GET /users/10
    ▼
    서버
    │
    │ 처리 결과 판단
    ▼
    Response
    │
    │ 200 / 404 / 500 ...
    ▼
    클라이언트
    ```
    
- **왜 200, 404, 500 처럼 숫자가 여러 개일까?**
  - 요청 결과를 성공, 실패 두 가지로만 표현하면 정보가 부족하다.
  - 실패했을 경우 `실패`라고만 나타내면
    - 클라이언트가 요청을 잘못한 건지
    - 로그인이 필요한 건지
    - 권한이 없는 건지
    - 요청한 리소스가 없는 건지
    - 서버 자체에 문제가 있는 건지  
  - 알 수 없다. 
  - 그래서 HTTP는 상태 코드를 여러 종류로 정의해놓았다.


- **상태 코드의 첫 번째 숫자가 중요하다.**
  - **응답은 5개의 그룹으로 나누어집니다.**
    ```text
    1xx → 정보를 제공하는 응답
    2xx → 성공적인 응답
    3xx → 리다이렉트
    4xx → 클라이언트 에러
    5xx → 서버 에러
    ```
  - 따라서 상태 코드를 처음 봤을 때는 첫 번째 숫자를 보면 어떤 종류의 응답인지 빠르게 파악할 수 있다.


- section 10 of RFC 2616
  - RFC 2616은 현재 폐기된 옛 HTTP/1.1 표준
  - 현재 HTTP 표준에서는 RFC 9110의 Section 15에서 상태 코드를 정의한다.
  - [section 15 of RFC 9110](https://datatracker.ietf.org/doc/html/rfc9110#section-15)

### 정보 응답
> 100 Continue 
> - 이 임시 응답은 지금까지 요청한 내용이 정상이며, 클라이언트가 요청을 계속 전송해도 된다는 것을 알려줍니다. 이미 요청을 모두 전송한 경우에는 이 응답을 무시할 수 있습니다.

> 101 Switching Protocols
> - 이 상태 코드는 클라이언트가 보낸 Upgrade 요청 헤더에 대한 응답으로 사용되며, 서버가 프로토콜을 변경할 것임을 나타냅니다.

> 102 Processing (WebDAV)
> - 이 상태 코드는 서버가 요청을 수신하여 처리하고 있지만, 아직 최종 응답을 반환할 준비가 되지 않았음을 나타냅니다.

> 103 Early Hints
> - 이 상태 코드는 주로 Link 헤더와 함께 사용되며, 서버가 최종 응답을 준비하는 동안 사용자 에이전트(User Agent)가 리소스의 사전 로딩(preloading)을 시작할 수 있도록 합니다.

- 1xx - 정보 제공
- 서버가 클라이언트에게 어떤 중간 정보(요청의 처리 과정에 대한 정보)를 알려주는 계열. **최종적인 처리 결과를 알려주는 응답이 아니다.**
- **처리 과정에서 전달되는 정보성/임시 응답**이다.

### 성공 응답
> **200 OK**
> - **요청이 성공적으로 되었습니다.** 성공의 의미는 HTTP 메소드에 따라 달라집니다.
>
> GET: 리소스를 가져와 메시지 바디에 담아 전송합니다.
>
> HEAD: 메시지 바디를 제외한 헤더를 전송합니다.
>
> PUT 또는 POST: 요청을 수행한 결과를 나타내는 리소스를 메시지 바디에 담아 전송합니다.
>
> TRACE: 메시지 바디에 서버가 수신한 요청 메시지가 포함됩니다.

> **201 Created**
> - **요청이 성공적이었으며 그 결과로 새로운 리소스가 생성되었습니다**. 이 응답은 일반적으로 POST 요청이나 일부 PUT 요청의 결과로 반환됩니다.

> **204 No Content**
> - 요청을 처리했지만 응답에 포함할 콘텐츠가 없습니다. 하지만 응답 헤더에는 의미 있는 정보가 포함될 수 있습니다. 사용자 에이전트는 캐시된 리소스의 헤더를 새로운 정보로 업데이트할 수 있습니다.

- 2xx - 서버가 요청을 성공적으로 처리
  - "성공"은 메서드에 따라 구체적인 의미가 다르다.
  - 그래서 `200`, `201`, `204`처럼 여러 성공 상태 코드가 존재한다.
  

- **200 OK**
  - 가장 기본적인 성공 응답.
  - `GET /users/10` 을 보냈고 서버가 사용자를 찾아서 보내줬다면
    ```text
    HTTP/1.1 200 OK
    Content-Type: application/json
   
    {
    "id": 10,
    "name": "영수"
    }
    ```
    가 될 수 있다.
  - ```text
    클라이언트
    │
    │ GET /users/10
    ▼
    서버
    │
    │ 10번 사용자 찾음
    ▼
    HTTP Response
    │
    │ 200 OK
    │
    │ { "id": 10, "name": "영수" }
    ▼
    클라이언트
    ```
    - 요청을 성공적으로 처리했다는 의미다.
    - GET처럼 결과를 전달하는 경우에는 Response Body에 그 결과가 포함될 수 있다.


- **201 Created**
  - 새로운 리소스가 만들어졌다.
  - 회원가입 API를 예시로
    - 클라이언트가 해당 요청을 보내면
    ```http
    POST /users
    Content-Type: application/json
        
    {
    "name": "영수",
    "age": 25
    }
    ```
    - 서버는 새로운 사용자를 생성한다.
    - 그러면 서버가 `HTTP/1.1 201 Created` 라고 응답할 수 있다.
    ```text
    POST
     ↓
    새로운 리소스 생성
     ↓
    201 Created
    ```
  - 200과 201의 차이
    - 둘 다 성공이지만 다음과 같이 보면 된다.
    - `GET /users/10` → `200 OK`
    - `POST /users` → `201 Created`
    ```text
    200 OK
    → 요청을 성공적으로 처리했다
  
    201 Created
    → 요청을 성공적으로 처리했고
    그 결과 새로운 리소스가 생성됐다
    ```

- **204 No Content**
  - 요청은 성공했지만, Response Body로 보내줄 내용은 없다.
  - 사용자를 삭제 할 경우,
    - `DELETE /users/10` → 서버가 성공적으로 삭제.
    - 굳이 `{"message": "삭제되었습니다."}` 를 Body에 넣어 보내지 않아도 된다.
    - 이럴 때 `HTTP/1.1 204 No Content` 라고 응답할 수 있다.
    ```text
    DELETE
    ↓
    삭제 성공
    ↓
    204 No Content
    ↓
    Response Body 없음
    ```

  - 200과 204의 차이
    - `DELETE /users/10` 요청 성공 후 :
      - 200 :
        ```http
        HTTP/1.1 200 OK
  
        {
        "message": "삭제 완료"
        }
        ```
      - 204 : <br>
        ```text
        HTTP/1.1 204 No Content
        ```
      ```text
      200 OK
      → 성공했고 Response Body를 보낼 수도 있음
 
      204 No Content
      → 성공했지만 Response Body에 보낼 내용이 없음
      ```
    - 둘 다 성공을 표현할 수 있지만 Response의 형태가 다르다.

### 리다이렉션 메시지
> 300 Multiple Choice
> - 요청에 대해 여러 가지 응답이 가능합니다. 사용자 에이전트 또는 사용자는 그중 하나를 선택해야 합니다. 응답 중 하나를 선택하는 방법에 대한 표준화된 방법은 없습니다.

> 301 Moved Permanently
> - 이 응답 코드는 **요청한 리소스의 URI가 영구적으로 변경**되었음을 의미합니다. 새로운 URI는 응답에 포함될 수 있습니다.

> 302 Found
> - 이 응답 코드는 **요청한 리소스가 일시적으로 다른 URI에 위치하고 있음**을 의미합니다. 따라서 클라이언트는 해당 리소스를 요청할 때 일시적으로 다른 URI를 사용할 수 있지만, 이후 요청에서는 원래 URI를 계속 사용해야 합니다.

> 303 See Other
> - 클라이언트가 요청한 리소스를 **다른 URI에서 GET 요청을 통해 가져와야 할 때**, 서버가 사용하는 응답입니다.

> 304 Not Modified
> - 이것은 **캐시된 리소스를 계속 사용할 수 있음**을 나타냅니다. 서버는 클라이언트가 이전에 캐시한 리소스가 변경되지 않았음을 알려주며, 클라이언트는 기존의 캐시된 리소스를 계속 사용할 수 있습니다.

> 307 Temporary Redirect
> - 클라이언트가 요청한 리소스가 다른 URI에 있으며, **이전 요청과 동일한 메서드를 사용하여 해당 URI로 요청**해야 할 때 서버가 사용하는 응답입니다. 이것은 302 Found HTTP 응답 코드와 비슷한 의미를 가지지만, 리다이렉트된 요청에서도 원래 HTTP 메서드를 그대로 유지해야 한다는 점이 다릅니다. 만약 첫 요청에 POST가 사용되었다면, 두번째 요청도 반드시 POST를 사용해야 합니다.

> 308 Permanent Redirect
> - 이것은 리소스가 이제 HTTP 응답 헤더의 Location에 명시된 **다른 URI로 영구적으로 이동했음**을 의미합니다. 이것은 301 Moved Permanently HTTP 응답 코드와 비슷한 의미를 가지지만, 리다이렉트된 요청에서도 원래 HTTP 메서드를 그대로 유지해야 한다는 점이 다릅니다. 만약 첫 요청에 POST가 사용되었다면, 두 번째 요청도 반드시 POST를 사용해야 합니다.

- 3xx
  - 서버가 클라이언트에게 현재 요청의 처리를 위해 다른 위치로 이동하거나, 다른 방식으로 처리해야 함을 알려주는 응답 계열


- **리다이렉션**
  - 요청한 리소스는 이 주소가 아닌 다른 주소로 가라는 의미
  - 사용자가 `https://example.com/old` 에 접속했지만 페이지가 `https://example.com/new` 로 이동했다면
  - 서버는 다음과 같은 응답을 보낼 수 있다.
    ```http
    HTTP/1.1 301 Moved Permanently
    Location: https://example.com/new
    ```
  - 그러면 브라우저가 `Location` 을 보고 새로운 주소로 다시 요청한다.
  - 전체 흐름은 다음과 같으며 3xx를 이해하는 핵심이 된다.
    ```text
    브라우저
    │
    │ GET /old
    ▼
    서버
    │
    │ 301 Moved Permanently
    │ Location: /new
    ▼
    브라우저
    │
    │ GET /new
    ▼
    서버
    │
    │ 200 OK
    ▼
    브라우저
    ```
    
- **301 Moved Permanently**
  - **요청한 리소스의 URI가 영구적으로(Permanently) 변경**
  - 원래 주소가 `https://example.com/old-page` 였는데 `https://example.com/new-page` 로 영구적으로 바뀌었다고 하자.
  - 서버는 이렇게 응답할 수 있다.
    ```http
    HTTP/1.1 301 Moved Permanently
    Location: https://example.com/new-page 
    ```
  - 브라우저는 새로운 주소로 요청한다.
    ```text
    GET /old-page
         ↓
    301
         ↓
    Location: /new-page
         ↓
    GET /new-page
         ↓
    200 OK
    ```
  - 앞으로 이 리소스는 여기 있다고 생각하라는 의미다.
  

- **302 Found**
  - **요청한 리소스의 URI가 일시적으로 변경**
  - 301과 비슷하지만 일시적이라는게 차이다.
- 301과 302에서의 문제
  - 리다이렉트가 발생하면 클라이언트는 새로운 URI로 다시 요청해야 한다.
  - 이때 **새로운 요청에서 HTTP Method를 어떻게 처리할지**가 중요하다.
  - `303`, `307`, `308`은 각각 리다이렉트된 요청을 어떻게 처리해야 하는지 명확하게 정의한다.


- **303 See Other**
  - 다른 주소로 GET 하라는 의미
  - 대표적인 상황이 POST 후 Redirect 이다.
    - 회원가입 `POST /users`를 보내고 서버가 사용자를 생성했다.
    - 생성 결과를 보여주는 페이지가 `/users/10`에 있다고 한다면 서버가 아래처럼 응답할 수 있다.
    ```http
    HTTP/1.1 303 See Other
    Location: /users/10
    ```
    - 그러면 클라이언트는 `GET /users/10` 으로 다시 요청한다.
    - 전체 흐름은 다음과 같다.
    ```text
    POST /users
        ↓
    서버에서 사용자 생성
        ↓
    303 See Other
    Location: /users/10
        ↓
    GET /users/10
        ↓
    200 OK
    ```
  - GET으로 보내는 이유
    - `POST /users` 회원가입 폼 제출 후 사용자가 새로고침을 눌렀을때 만약 브라우저가 이전 POST를 그대로 다시 실행한다면
    ```text
    POST /users
    POST /users
    POST /users
    ```
    - 이처럼 같은 생성이 반복될 위험이 있다.
    - 그래서 웹에서는 흔히 다음과 같은 패턴을 사용한다.
    ```text
    POST
     ↓
    303 Redirect
     ↓
    GET
    ```
    - POST/Redirect/GET(PRG) 패턴이라고 부르기도 한다.
    - 핵심은 **POST로 작업을 수행한 뒤, 결과를 보여주는 페이지로 GET 요청을 보내도록 할 수 있다.**


- **304 Not Modified**
  - 현재 가지고 있는 캐시 버전 그대로 사용해도 된다는 의미
  - 서버에서 `HTTP/1.1 304 Not Modified` 라는 답이 오면 브라우저는 기존 캐시를 사용한다.
  - 새로운 리소스 데이터를 다시 보내는 대신, 클라이언트가 기존에 가지고 있는 캐시된 리소스를 사용하도록 하는 응답이다.


- **307 Temporary Redirect**
  - 이전 요청과 동일한 메서드를 사용하여 요청해야 할 때
  ```text
  클라이언트
  │
  │ POST /old
  ↓
  서버
  │ 307 Temporary Redirect
  │ Location: /new
  ↓
  클라이언트
  │   
  │POST /new
  ↓
  서버
  ```
  - GET으로 바꾸면 안되고 `POST /new`로 요청해야 한다.
- 302와 307의 차이  
  ```text
  302
  → 임시로 다른 곳으로 이동
  
  307
  → 임시로 다른 곳으로 이동
     + HTTP Method를 그대로 유지
  ```
  - HTTP Specification 에서는 Method를 그대로 유지해야 한다는 의미를 명확하게 표현하고 싶을 때 307을 사용한다.


- **308 Permanent Redirect**
  - 301과 짝으로 생각하면 쉽다
  ```text
  301
  → 영구 리다이렉트
   
  308
  → 영구 리다이렉트 + Method 유지
  ```
  
```text
301 → 영구
308 → 영구 + Method 유지

302 → 임시
307 → 임시 + Method 유지

303 → 다른 URI를 GET으로 요청

304 → 캐시된 리소스를 계속 사용해도 됨
```

### 클라이언트 에러 응답

> **400 Bad Request**
> - 이 응답은 **잘못된 문법으로 인하여 서버가 요청을 이해할 수 없음**을 의미합니다.

> **401 Unauthorized**
> - HTTP 표준에서는 이 상태를 "미승인(unauthorized)"이라고 표현하지만, 실제 의미는 "**비인증**(unauthenticated)"에 가깝습니다. 클라이언트는 요청한 응답을 받기 위해 자신을 인증해야 합니다.

> **403 Forbidden**
> - 클라이언트는 요청한 콘텐츠에 접근할 권한이 없습니다. 서버는 요청을 이해했지만 이를 수행하기를 거부합니다. 401과 다른 점은 **서버가 클라이언트의 신원을 알고 있을 수 있다**는 것입니다.

> **404 Not Found**
> - 서버가 요청받은 리소스를 찾을 수 없습니다. 브라우저에서는 존재하지 않는 URL을 의미할 수 있습니다. API에서는 엔드포인트 자체는 존재하지만 요청한 리소스가 존재하지 않는 경우에도 사용할 수 있습니다. 또한 서버가 인증되지 않은 클라이언트에게 리소스의 존재 여부를 숨기기 위해 403 대신 404를 반환할 수도 있습니다. 이 응답 코드는 웹에서 반복적으로 발생하기 때문에 가장 유명할지도 모릅니다.

> **405 Method Not Allowed**
> - 요청에 사용된 메서드는 서버가 알고 있지만, 대상 리소스에서는 해당 메서드를 사용할 수 없습니다. 예를 들어, 어떤 API에서 리소스를 삭제하는 것을 금지할 수 있습니다. 필수적인 메소드인 GET과 HEAD는 제거될 수 없으며 이 에러 코드를 리턴할 수 없습니다.

> **409 Conflict**
> - 이 응답은 요청이 **현재 서버의 상태와 충돌될 때** 보냅니다.

> 415 Unsupported Media Type
> - 요청에 포함된 미디어 형식을 서버가 지원하지 않습니다. 따라서 서버는 해당 요청을 거부합니다.

> 422 Unprocessable Entity (WebDAV)
> - 요청의 형식은 올바르지만, 포함된 내용을 처리할 수 없습니다.

> 429 Too Many Requests
> - 사용자가 주어진 시간 동안 너무 많은 요청을 보냈습니다. ("rate limiting").

- 4xx
  - 클라이언트의 **요청**에 문제가 있는 상황


- **400 Bad Request**
  - 요청 자체에 문제가 있음
  - 서버가 요청을 제대로 처리할 수 없음


- **401 Unauthorized**
  - 인증 필요 / 인증되지 않음
  - 서버가 사용자가 누구인지 알 수 없는 상태(인증이 필요하거나 인증에 실패)
    - 인증 정보 없음
    - 인증 정보 잘못됨
    - 인증 정보 만료됨
  - 로그인 하지 않은 사용자가 `GET /mypage` 를 요청한다면 `401 Unauthorized`
  - 인증(Authentication)이란
    ```text
    아이디/비밀번호
    토큰
    세션
    ...
    ```
    등을 이용해서 사용자를 확인하는 것.


- **403 Forbidden**
  - 인증은 됐지만 권한 없음
  - 관리자 전용 페이지에 일반 사용자 A가 로그인 할 경우 서버는 A가 누구인지 알지만 권한은 없다.
  - 그러면 `403 Forbidden`을 보낼 수 있다.

  - 401 vs 403
    ```text
    401
    → 사용자가 누구인지 모른다.(인증이 필요하거나 인증에 실패함)
    → 인증(Authentication) 문제
    
    403
    → 사용자가 누구인지 안다.
    → 하지만 접근할 권한 없음.
    → 인가(Authorization) 문제
    ```

- **404 Not Found**
  - 리소스 없음
  - `GET /users/100`을 요청했는데 서버에 100번 사용자가 없다.
  - 그러면 `404 Not Found`가 될 수 있다.
  - 단순히 "URL 틀림" 만을 의미하지 않는다.
    - `GET /users/999` 라는 URL 자체는 올바른 API 주소일 수 있다. 그런데 `999번 사용자 없음`이면 404가 될 수 있다.
      - 요청할 API 주소 자체가 존재하지 않음 → 404
      - API 주소는 존재하지만 그 안에서 찾으려는 리소스가 없음 → 404

  
- **405 Method Not Allowed**
  - 해당 메서드를 사용할 수 없음
  - 서버에 `/users` 라는 리소스가 있을때, `GET /users`는 허용되어 있고 `DELETE /users`는 허용하지 않는 API일 경우 `405 Method Not Allowed`가 될 수 있다. 


- 409 Conflict
  - 현재 서버 상태와 충돌
  - 회원가입 API에서 사용자가 `아이디 = name` 으로 가입하려고 한다. 그런데 이미 `name`이라는 사용자가 존재한다.
    ```text
    요청 형식이 틀림 ❌
    서버가 고장남 ❌
    
    현재 서버 상태와 충돌함 ✅
    ```
  - 이 상황은 위처럼 볼 수 있다.
  - 그래서 `409 Conflict`를 사용할 수 있다.


- 415 Unsupported Media Type
  - 요청 데이터 형식을 서버가 지원하지 않음
  - 클라이언트가 데이터를 서버가 지원하지 않는 형식으로 보내면 `415 Unsupported Media Type`이 될 수 있다.
  - Media Type 이란
    - application/json
    - text/html
    - text/plain 등


- 422 Unprocessable Entity
  - 요청은 이해했지만 내용이 유효하지 않음
  - JSON이 `{"age": -500}`이면 문법 자체는 정상이고 서버도 JSON이라는 것을 이해할 수 있다.
  - 애플리케이션 규칙상 **나이는 -500살일 수 없음** 이다. 이 경우 `422`를 사용할 수 있다.

- 429 Too Many Requests
  - 요청 너무 많이 보냄
  - 1분에 최대 100번 이라는 제한이 있는데 1분에 10,000번 요청을 보냈다면 서버가 `429`를 반환할 수 있다.
  - 이걸 Rate Limiting이라고 한다.
  - Rate Limiting은
    ```text
    무한 요청
    → 서버 부담
    → 악용 가능
    ```
    을 막기 위해 사용한다.

## 서버 에러 응답
> 500 Internal Server Error
> - 서버에서 예상하지 못한 문제가 발생하여 요청을 처리할 수 없습니다.

> 502 Bad Gateway
> - 이 오류 응답은 서버가 요청을 처리하는 데 필요한 응답을 얻기 위해 게이트웨이로 작업하는 동안 **잘못된 응답을 수신했음**을 의미합니다.

> 503 Service Unavailable
> - 서버가 요청을 처리할 준비가 되지 않았습니다. 일반적인 원인은 **유지보수를 위해 작동이 중단되었거나 과부하가 발생한 경우**입니다. 이 응답은 임시적인 상황에 사용해야 하며, 가능하다면 Retry-After 헤더를 통해 서비스를 다시 이용할 수 있을 것으로 예상되는 시간을 알려줄 수 있습니다.

> 504 Gateway Timeout
> - 이 오류 응답은 서버가 게이트웨이 역할을 하고 있으며 **적절한 시간 내에 응답을 받을 수 없을 때** 발생합니다.

- 5xx
  - 서버 쪽에서 요청을 처리하지 못함


- **500 Internal Server Error**
  - 서버 내부에서 예상하지 못한 문제 발생
  - `500`은 **굉장히 범용적인 서버 내부 오류다**
  - 개발할 때 서버 로그를 보다가 `500 Internal Server Error`가 발생하면
  - "서버 내부에서 뭔가 터졌구나. 서버 로그를 확인해야겠다." 라고 생각해야 한다.


- 502 Bad Gateway
  - 게이트웨이가 다른 서버와 통신하면서 그 서버로부터 잘못된 응답을 받으면 `502`가 발생할 수 있다.


- 503 Service Unavailable
  - 서버가 현재 요청을 처리할 준비가 되어 있지 않다.
  - 대표적인 상황
    - 서버 점검 중
    - 서버 과부하
    - 일시적인 장애
  - **일시적인 상황**을 나타낼 때 사용한다.


- 504 Gateway Timeout
  - 게이트웨이가 뒤쪽 서버로부터 제때 응답을 받지 못함. **시간 초과(timeout)**
