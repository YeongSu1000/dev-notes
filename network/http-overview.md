#HTTP
> 참고 자료: [MDN - HTTP 개요](https://developer.mozilla.org/ko/docs/Web/HTTP/Guides/Overview)

MDN의 HTTP 개요를 기반으로 HTTP의 기본 개념을 학습하고 정리한 노트입니다.

## HTTP 개요

> HTTP는 HTML 문서와 같은 **리소스들을 가져올 수 있도록 해주는 프로토콜**입니다.

- **프로토콜**: 서로 통신할 때 지켜야 하는 약속
    - 어떤 형식으로 메시지를 주고받을지에 대한 규칙
    - 프로그램이나 데이터 자체가 아니라, **통신을 위한 규칙**
- **리소스**: 웹에서 가져올 수 있는 대상
    - HTML, CSS, JavaScript, 이미지, 동영상, 폰트, JSON, 데이터 등

> HTTP는 웹에서 이루어지는 모든 데이터 교환의 기초이며, 클라이언트-서버 프로토콜이기도 합니다.

- **클라이언트**: 서버에게 무언가를 요청하는 쪽
    - 보통 웹 브라우저
    - Java/Spring에서는 프로그램이 다른 서버에 HTTP 요청을 보내는 경우도 볼 수 있다.

- **서버**: 클라이언트의 요청을 받아서 처리하고 응답하는 쪽

  ```
  쇼핑몰 접속 시
  [Chrome] 클라이언트
         ↓ HTTP Request
  [쇼핑몰 서버] 서버
         ↓ HTTP Response
  [Chrome] 클라이언트
  ```

- **클라이언트-서버 프로토콜**
    - 클라이언트가 요청을 시작하고 서버가 그 요청에 응답하는 구조
    - Client → Request → Server → Response → Client

> 클라이언트-서버 프로토콜이란 (보통 웹브라우저인) 수신자 측에 의해 요청이 초기화되는 프로토콜을 의미합니다. 하나의
> 완전한 문서는 텍스트, 레이아웃 설명, 이미지, 비디오, 스크립트 등 불러온(fetched) 하위 문서들로 재구성됩니다.

1. 사용자가 주소를 입력
2. 브라우저가 클라이언트 역할
3. 브라우저가 서버에게 HTTP Request를 보낸다
4. 서버가 요청을 처리한다
5. 서버가 HTTP Response를 보낸다
6. 브라우저가 받은 리소스를 이용해 웹페이지를 구성한다
    + 그리고 HTML 안에서 추가로 필요한 CSS, JavaScript, 이미지 등이 있다면 그것들을 다시 요청할 수도 있다.

> 클라이언트와 서버들은 (데이터 스트림과 대조적으로) 개별적인 메시지 교환에 의해 통신합니다. 보통 브라우저인 클라이언트에 의해 전송되는 메시지를 요청(requests)이라고 부르며, 그에 대해 서버에서 응답으로
> 전송되는 메시지를 응답(responses)이라고 부릅니다.

```
             HTTP 메시지
                  │
        ┌─────────┴─────────┐
        ↓                   ↓
     Request             Response
        ↓                   ↓
 클라이언트 → 서버      서버 → 클라이언트
 ```

- Request = 클라이언트가 서버로 보내는 HTTP 메시지
- Response = 서버가 클라이언트로 보내는 HTTP 메시지

> 1990년대 초에 설계된 HTTP는 거듭하여 진화해온 **확장 가능한** 프로토콜입니다. HTTP는 **애플리케이션 계층**의 프로토콜로, 신뢰 가능한 전송 프로토콜이라면 이론상으로는 무엇이든 사용할 수 있으나
> TCP 혹은 암호화된 TCP 연결인 TLS를 통해 전송됩니다. HTTP의 확장성 덕분에, 오늘날 하이퍼텍스트 문서 뿐만 아니라 이미지와 비디오 혹은 HTML 폼 결과와 같은 내용을 서버로 포스트(POST)하기
> 위해서도 사용됩니다. HTTP는 또한 필요할 때마다 웹 페이지를 갱신하기 위해 문서의 일부를 가져오는데 사용될 수도 있습니다.

- **확장 가능하다**: 기존의 기본 구조를 유지하면서 새로운 기능을 추가하고 발전시킬 수 있다
- **애플리케이션 계층**: 애플리케이션이 데이터를 어떤 의미와 규칙으로 주고받을지를 정의하는 계층
    - HTTP가 여기에 해당한다.
- **TLS**: HTTP 통신을 암호화하여 보호하는 기술
    - HTTPS는 HTTP에 TLS를 적용한 것이다.

**핵심**

1. HTTP는 애플리케이션 계층의 프로토콜이다.
    - 웹에서 데이터를 주고받기 위한 규칙을 정의한다.

2. HTTP가 혼자 데이터를 전달하는 것은 아니다.
    - 아래 처럼 다른 네트워크 기술과 함께 동작한다.

    ```
    ┌─────────────────┐
    │      HTTP       │ ← 웹 통신 규칙
    ├─────────────────┤
    │      TCP        │ ← HTTP 데이터를 전달하는 전송 프로토콜
    ├─────────────────┤
    │       IP        │ ← 목적지를 찾아 전달
    └─────────────────┘
    ```

3. HTTP는 HTML만 주고받는 기술이 아니다.
    - 아래 처럼 다양한 데이터를 주고받을 수 있다.

    ```
    HTML
    이미지
    동영상
    JSON
    폼 데이터
    ```

4. HTTP는 서버에서 가져오는 것뿐만 아니라 서버로 보내는 데도 사용된다.

    ```
    회원 가입 페이지
    아이디: youngsu
    비밀번호: ****
    
    브라우저
       │
       │ POST Request
       │
       │ "회원가입 데이터를 보냅니다."
       ▼
      서버
    ```

## HTTP 기반 시스템의 구성요소

> HTTP는 클라이언트-서버 프로토콜입니다. 요청은 하나의 개체, **사용자 에이전트**(또는 그것을 대신하는 프록시)에 의해 전송됩니다. 대부분의 경우, 사용자 에이전트는 브라우저지만, 무엇이든 될 수 있습니다.
> 예를 들어, 검색 엔진 인덱스를 채워넣고 유지하기 위해 웹을 돌아다니는 로봇이 그러한 경우입니다.

- **사용자 에이전트(User Agent)**: 사용자를 대신해서 서버와 통신하는 프로그램
    - 대표적으로 아래와 같은 웹 브라우저
    - 사용자가 직접 HTTP 메시지를 작성하지 않아도 브라우저가 사용자의 행동을 바탕으로 HTTP Request를 만들어 서버에 보낸다.

      ```
      Chrome
      Firefox
      Edge
      Safari
      ```
      
      ```
      사용자 
      │  주소 입력 / 버튼 클릭 / 링크 클릭
      │  
      ▼
      브라우저
      │
      │ HTTP Request
      ▼
      서버
      ```

- **사용자 에이전트 ≠ 브라우저**
    - 브라우저가 사용자 에이전트인 경우가 가장 흔하지만, HTTP 요청을 만들 수 있는 프로그램이라면 다른 것도 가능하다.
    - MDN에서 예로 든 게 검색 엔진 로봇이다.
- **클라이언트와 사용자 에이전트의 관계**
    - 클라이언트는 HTTP 요청을 보내는 측을 의미한다.
    - 사용자 에이전트(User Agent)는 사용자를 대신해 HTTP 요청을 보내는 프로그램을 의미한다.
    - 웹에서는 브라우저가 대표적인 사용자 에이전트이자 클라이언트이다.

> 각각의 개별적인 요청들은 서버로 보내지며, 서버는 요청을 처리하고 response라고 불리는 응답을 제공합니다. 이 요청과 응답 사이에는 여러 개체들이 있는데, 예를 들면 다양한 작업을 수행하는 게이트웨이 또는
> 캐시 역할을 하는 프록시 등이 있습니다.

- **프록시(Proxy)**: 클라이언트와 서버 사이에서 클라이언트를 대신해 HTTP 요청을 전달하는 중간 구성요소
    - 요청이나 응답을 전달하는 과정에서 캐싱, 필터링, 인증 등의 작업을 수행할 수 있다.
- **게이트웨이**: HTTP 요청을 받아서 다른 시스템이나 서비스와 연결해주는 중간 역할을 할 수 있는 구성요소

  ```
  사용자
    │
    ▼
  브라우저
  (User Agent)
    │
    │ HTTP Request
    ▼
  [필요한 경우]
  프록시 / 캐시 / 게이트웨이 등
    │
    │ HTTP Request
    ▼
  서버
    │
    │ HTTP Response
    ▼
  [필요한 경우]
  프록시 / 캐시 / 게이트웨이 등
    │
    │ HTTP Response
    ▼
  브라우저
  ```

- **캐시**: 이전에 가져온 데이터를 저장해두었다가 필요할 때 다시 사용하는 것

  ```
  서버에 매번 요청
  → 느릴 수 있음
  
  캐시에 저장된 데이터 사용
  → 서버까지 요청하지 않아도 됨
  ```

**핵심**  
```HTTP 통신은 단순히 "브라우저와 서버가 직접 대화한다"가 아니라, 브라우저 같은 User Agent가 클라이언트 역할을 하여 HTTP Request를 보내고, 그 메시지가 필요에 따라 여러 중간 구성요소를 거쳐 서버에 도착한 뒤, HTTP Response가 다시 돌아오는 구조다.```

> 실제로는 브라우저와 요청을 처리하는 서버 사이에는 좀 더 많은 컴퓨터들이 존재합니다: 라우터, 모뎀 등이 있죠. 웹의 계층적인 설계 덕분에, 이들은 네트워크와 전송 계층 내로 숨겨집니다. HTTP은 애플리케이션
> 계층의 최상위에 있습니다. 네트워크 문제를 진단하는 것도 중요하지만, 기본 레이어들은 HTTP의 명세와는 거의 관련이 없습니다.

### 클라이언트: 사용자 에이전트

> 사용자 에이전트는 사용자를 대신하여 동작하는 모든 도구입니다. 이 역할은 주로 브라우저에 의해 수행됩니다; 엔지니어들과 자신들의 애플리케이션을 디버그하는 웹 개발자들이 사용하는 프로그램들은 예외입니다.

> 브라우저는 항상 요청을 보내는 개체입니다. 그것은 결코 서버가 될 수 없습니다(수년에 걸쳐 서버 초기화된 메시지를 시뮬레이션하기 위해 몇 가지 메커니즘이 추가되어 왔지만).

> 웹 페이지를 표시하기 위해, 브라우저는 페이지의 HTML 문서를 가져오기 위한 요청을 전송한 뒤, 파일을 구문 분석하여 실행해야 할 스크립트 그리고 페이지 내 포함된 하위 리소스들(보통 이미지와 비디오)을 잘
> 표시하기 위한 레이아웃 정보(CSS)에 대응하는 추가적인 요청들을 가져옵니다. 그런 뒤에 브라우저는 완전한 문서인 웹 페이지를 표시하기 위해 그런 리소스들을 혼합합니다. 브라우저에 의해 실행된 스크립트는 이후
> 단계에서 좀 더 많은 리소스들을 가져올 수 있으며 브라우저는 그에 따라 웹 페이지를 갱신하게 됩니다.

```
사용자
  │  example.com
  │ "웹사이트 열어줘"
  ▼
브라우저
  │
  │ Request
  ▼
서버
  │
  │ Response: HTML
  ▼
브라우저
  │
  ├── HTML 분석
  │
  ├── Request → CSS
  ├── Request → 이미지
  ├── Request → JavaScript
  │
  └── JavaScript 실행
          │
          └── 추가 Request → 서버
                           │
                           └── Response: JSON 등
```

> 웹 페이지는 하이퍼텍스트 문서로, 표시된 텍스트의 일부는 사용자가 사용자 에이전트를 제어하고 웹을 돌아다닐 수 있도록 새로운 웹 페이지를 가져오기 위해 실행(보통 마우스 클릭에 의해)될 수 있는 링크임을
> 뜻합니다. 브라우저는 HTTP 요청 내에서 이런 지시 사항들을 변환하고 HTTP 응답을 해석하여 사용자에게 명확한 응답을 표시합니다.

```
사용자
  │
  │ 클릭 / 주소 입력 / 버튼 클릭
  ▼
브라우저
  │
  │ HTTP Request
  ▼
서버
  │
  │ HTTP Response
  ▼
브라우저
  │
  │ 화면으로 변환
  ▼
사용자
```

**핵심**

1. 브라우저는 사용자의 행동을 계기로 HTTP Request를 만들어 서버에 보낸다.

    ```
    사용자가 링크 클릭
            ↓
    브라우저
            ↓
    HTTP Request
            ↓
    서버
    ```

2. 웹페이지 하나를 만드는 데 여러 HTTP Request가 발생할 수 있다.

    ```
    HTML을 받은 브라우저
            ↓
    HTML 분석
            ↓
    필요한 CSS / JavaScript / 이미지 등을 각각 요청
            ↓
    리소스를 받아 페이지 구성
            ↓
    JavaScript 실행
            ↓
    필요하면 추가 요청
    ```

   - **"페이지 하나 = HTTP 요청 하나"가 아니다.**

3. 브라우저는 Response를 받아서 사람이 보는 화면으로 만든다.

    ```
    HTTP Response
         ↓
    브라우저가 해석
         ↓
    HTML + CSS + JS + 이미지
         ↓
    화면
    ```

### 웹 서버

> 통신 채널의 반대편에는 클라이언트에 의한 요청에 대한 문서를 제공하는 서버가 존재합니다. 서버는 사실 상 **논리적으로 단일 기계**입니다.이는 로드(로드 밸런싱) 혹은 그때 그때 다른 컴퓨터(캐시, DB 서버,
> e-커머스 서버 등과 같은)들의 정보를 얻고 완전하게 혹은 **부분적으로 문서를 생성**하는 소프트웨어의 복잡한 부분을 공유하는 서버들의 집합일 수도 있기 때문입니다.

- **논리적으로 단일 기계**
    - 클라이언트 입장에서는 하나의 서비스(서버)에 요청하고 응답받는 것처럼 보인다.
    - 실제로는 여러 서버와 컴퓨터가 역할을 나누어 처리할 수 있다.
        
      ```
                      쇼핑몰 시스템
                           │
             ┌─────────────┼─────────────┐
             ↓             ↓             ↓
         웹 서버 A      웹 서버 B      웹 서버 C
             │             │             │
             └─────────────┼─────────────┘
                           ↓
                        DB 서버
      ```

- **부분적으로 문서를 생성**
  - ```GET /products``` 요청이 들어오면 서버가 DB에서 상품 A, B, C를 가져온 다음 필요한 데이터를 조합해서 Response를 만들어 낼 수 있다.
  - 아래는 Spring Boot 웹 애플리케이션을 예로 든 것이다.
    ```
    상품 A
    상품 B
    상품 C
    ```
    ```
    HTTP Request
          ↓
    Spring Boot
          ↓
    DB 조회
          ↓
    데이터 가공
          ↓
    HTTP Response
    ```
> 서버는 반드시 단일 머신일 필요는 없지만, 여러 개의 서버를 동일한 머신 위에서 호스팅 할 수는 있습니다. HTTP/1.1과 Host 헤더를 이용하여, 동일한 IP 주소를 공유할 수도 있습니다.
- 한 컴퓨터에서 여러 서버도 가능하고, 여러 컴퓨터가 하나의 서비스를 구성 할 수 있다.
    ```
    컴퓨터 한 대
    ├── 서버 A
    ├── 서버 B
    └── 서버 C
    ```
    ```
    컴퓨터 A ─┐
    컴퓨터 B ─┼→ 하나의 웹 서비스
    컴퓨터 C ─┘
    ```
**핵심**
```서버 = 컴퓨터 한 대 라는 생각은 하면 안된다.```

### 프록시
> 웹 브라우저와 서버 사이에서는 수많은 컴퓨터와 머신이 HTTP 메시지를 이어 받고 전달합니다.
> 여러 계층으로 이루어진 웹 스택 구조에서 이러한 컴퓨터/머신들은 대부분은 **전송, 네트워크 혹은 물리 계층에서 동작하며,
> 성능에 상당히 큰 영향을 주지만 HTTP 계층에서는 이들이 어떻게 동작하는지 눈에 보이지 않습니다. 
> 이러한 컴퓨터/머신 중에서도 **애플리케이션 계층에서 동작하는 것들을 일반적으로 프록시**라고 부릅니다. 
> **프록시는 눈에 보이거나 그렇지 않을 수도 있으며**
> 다양한 기능들을 수행할 수 있습니다:
>- 캐싱 (캐시는 공개 또는 비공개가 될 수 있습니다 (예: 브라우저 캐시))  
>- 필터링 (바이러스 백신 스캔, 유해 컨텐츠 차단(자녀 보호) 기능)  
>- 로드 밸런싱 (여러 서버들이 서로 다른 요청을 처리하도록 허용)  
>- 인증 (다양한 리소스에 대한 접근 제어)  
>- 로깅 (이력 정보를 저장)  

- **애플리케이션 계층에서 HTTP 메시지를 다루는 중간 시스템을 일반적으로 프록시라고 부른다.**
  - 프록시는 HTTP를 이해하고 처리할 수 있다.
  - 따라서 단순히 데이터를 전달하는 것뿐만 아니라 HTTP 메시지를 바탕으로 다양한 작업을 수행할 수 있다.

    ```
    브라우저
      │
      │ HTTP Request
      ▼
    프록시
      │
      │ HTTP Request
      ▼
    서버
      │
      │ HTTP Response
      ▼
    프록시
      │
      │ HTTP Response
      ▼
    브라우저
    ```
- **눈에 보이는 프록시 / 보이지 않는 프록시**
  - 클라이언트가 프록시의 존재를 알고 있는지 여부와 관련된 표현이다.
  - 프록시는 HTTP 메시지를 중간에서 처리하거나 필요에 따라 변경할 수 있다.
    ```
    브라우저
       │
       │ Request A
       ▼
    프록시
       │
       │ Request B
       ▼
    서버
    ```

- **캐싱**: 데이터를 저장해두고 재사용하는 것
- **필터링**: 요청이나 응답을 검사하여 허용하거나 차단하는 것
- **로드 밸런싱**: 여러 서버에 요청을 나누어 보내는 것
- **인증**: 사용자가 누구인지 확인하는 것
- **로깅**: 요청이나 처리 결과 등의 기록을 남기는 것

**핵심**  
```라우터 등 네트워크 장비는 HTTP 자체를 처리하는 것이 아니라 주로 네트워크 계층 등의 역할을 수행한다.```  

```반면 프록시는 애플리케이션 계층에서 HTTP 메시지를 처리할 수 있기 때문에 HTTP 내용을 바탕으로 다양한 작업을 수행할 수 있다.```
```
일반적인 네트워크 장비
        ↓
HTTP보다 아래 계층에서 동작
        ↓
HTTP 내용을 직접 다루지 않음
```
```
프록시
        ↓
애플리케이션 계층에서 동작
        ↓
HTTP 메시지를 처리할 수 있음
        ↓
캐싱 / 필터링 / 로드 밸런싱 / 인증 / 로깅
```

## HTTP의 기초적인 측면
### HTTP는 간단합니다
> **HTTP는 사람이 읽을 수 있으며 간단**하게 고안되었습니다. 심지어 HTTP/2가 다소 더 복잡해졌지만 여전히 HTTP 메세지를 프레임별로 캡슐화하여 간결함을 유지하였습니다. HTTP 메시지들은 사람이 읽고 이해할 수 있어, 테스트하기 쉽고 초심자의 진입장벽을 낮췄습니다.

- **HTTP는 사람이 읽고 이해할 수 있는 형태로 표현된다.**
  - 아래와 같은 메시지를 개발자가 직접 보고 이해할 수 있다.
    ```http
    GET /products HTTP/1.1
    Host: example.com
    ```
  - 그래서 테스트와 디버깅이 비교적 쉽다.
    - 문제가 생겼을때 아래 내용들을 직접 확인할 수 있다.
    ```text
    어떤 Method를 사용했는지
    어떤 경로를 요청했는지
    어떤 Header가 들어갔는지
    어떤 Response가 왔는지
    ```
### HTTP는 확장 가능합니다
> HTTP/1.0에서 소개된, HTTP 헤더는 HTTP를 확장하고 실험하기 쉽게 만들어주었습니다. 클라이언트와 서버가 **새로운 헤더의 시맨틱에 대해 간단한 합의**만 한다면, 언제든지 새로운 기능을 추가할 수 있습니다.

- **확장 가능하다 의미**: Header를 통해 기존 구조를 크게 바꾸지 않고도 새로운 정보를 전달하고 기능을 확장할 수 있다.

    ```text
    HTTP Request
    ┌──────────────────────────────┐
    │ GET /users HTTP/1.1          │
    │ Host: example.com            │
    │ Accept: application/json     │ ← Header
    │ 새로운 정보: 값                │ ← Header를 추가할 수 있음
    └──────────────────────────────┘
    ```
    - Header를 새로 만들거나 사용할 때는 그 Header가 어떤 의미인지 클라이언트와 서버가 알고 있어야 한다.

- **새로운 헤더의 시맨틱에 대해 간단한 합의**
    - 시맨틱(semantics)은 해당 헤더가 **무슨 의미를 가지는지**를 말한다.
    - 새로운 Header를 사용하려면 클라이언트와 서버가 그 Header의 이름뿐만 아니라 **그 Header가 어떤 의미로 사용되는지도 알고 있어야 한다.**
    - 즉, `Header 이름 + 그 Header가 의미하는 것`에 대한 약속이 필요하다.
- **Header + 의미에 대한 약속 = HTTP를 확장하는 방법**

## HTTP는 상태가 없지만 세션은 있습니다
> HTTP는 상태를 저장하지 않습니다(Stateless). 동일한 연결 상에서 연속하여 전달된 두 개의 요청 사이에는 연결고리가 없습니다. 이는 e-커머스 쇼핑 바구니처럼, 일관된 방식으로 사용자가 페이지와 상호작용하길 원할 때 문제가 됩니다. 하지만, HTTP의 핵심은 상태가 없는 것이지만 **HTTP 쿠키는 상태가 있는 세션을 만들도록 해줍니다**. 헤더 확장성을 사용하여, 동일한 컨텍스트 또는 동일한 상태를 공유하기 위해 각각의 요청들에 세션을 만들도록 HTTP 쿠키가 추가됩니다.
- **상태**: 서버가 이전에 일어난 일을 기억하고 있는 정보
  - Stateless: HTTP 프로토콜 자체가 각각의 요청을 이전 요청과 자동으로 연결해서 상태를 유지하지 않는다.
- **HTTP의 핵심은 상태가 없는 것이지만 HTTP 쿠키는 상태가 있는 세션을 만들도록 해줍니다.**
  - HTTP는 원래 서로 다른 요청을 기억하지 않지만, 쿠키 같은 메커니즘을 이용하면 "이 요청이 누구의 것인지"를 연결할 수 있다.
  - HTTP Cookie는 HTTP Header를 통해 전달된다.
  - 서버는 `Set-Cookie` Header를 통해 브라우저에 쿠키를 저장하도록 할 수 있다.
  - 브라우저는 이후 요청에서 `Cookie` Header를 통해 해당 쿠키를 서버에 보낸다.
    ```text
    브라우저
       │
       │ 로그인 요청
       ▼
    서버
       │
       │ Set-Cookie: sessionId=ABC123
       ▼
    브라우저
       │
       │ Cookie: sessionId=ABC123
       ▼
    서버
       │
       │ "ABC123에 해당하는 세션 정보 확인"
       ▼
    응답
    ```
    - 이렇게 되면 여러 Request가 하나의 사용자 세션과 연결될 수 있다.
  

- **세션**: 여러 HTTP 요청을 하나의 사용자/상태로 묶어서 관리하는 것 
    ```text
    로그인
       ↓
    sessionId = ABC123
       ↓
    상품 조회
       ↓
    장바구니 추가
       ↓
    주문 페이지
    ```
    - 이 여러 요청을 서버가 `같은 세션에 속한 요청이다.` 라고 연결할 수 있다.  

- **Cookie와 Session은 같은 것이 아니다.**
    - Cookie는 브라우저와 서버가 HTTP 요청/응답을 통해 주고받는 데이터이다.
    - Session은 여러 요청을 하나의 사용자/상태와 연결하여 관리하는 개념이다.
    - 흔히 Cookie에 Session ID를 저장하여 사용자의 요청과 서버의 Session을 연결한다.

- Cookie와 Session 같은 메커니즘을 이용하면 여러 HTTP Request를 같은 사용자/상태와 연결할 수 있다.
    ```text
    HTTP
     └─ 기본적으로 Stateless
    
    Cookie / Session 등의 메커니즘
     └─ 여러 요청을 연결
            ↓
        상태 유지 가능
    ```

**핵심**
```text
HTTP
 ↓
기본적으로 Stateless
 ↓
각 요청은 서로 독립적
 ↓
Cookie 등을 이용해 Session ID 전달
 ↓
서버가 Session ID를 통해 Session 확인
 ↓
여러 요청을 같은 사용자/상태와 연결
```

## HTTP와 연결
>**연결은 전송 계층에서 제어**되므로 근본적으로 HTTP 영역 밖입니다. HTTP는 연결될 수 있도록 하는 근본적인 전송 프로토콜을 요구하지 않습니다. 다만 그저 신뢰할 수 있거나 메시지 손실이 없는(최소한의 오류는 표시) 연결을 요구할 뿐입니다. 인터넷 상의 가장 일반적인 두 개의 전송 프로토콜 중에서 TCP는 신뢰할 수 있으며 UDP는 그렇지 않습니다. 그러므로 **HTTP는 연결이 필수는 아니지만 연결 기반인 TCP 표준에 의존**합니다.
- **연결은 전송 계층에서 제어**
  - HTTP와 TCP는 서로 다른 역할
    - HTTP: 어떤 데이터를 주고받을 것인가
    - TCP: 그 데이터를 안정적으로 전달할 수 있게 어떻게 통신할 것인가
- **TCP**: 데이터를 제대로 전달하기 위한 기능이 있는 전송 프로토콜
  - 신뢰성 있는 데이터 전달을 중요하게 생각
- **UDP**: TCP보다 단순하게 데이터를 보내는 전송 프로토콜
  - 신뢰성보다 단순하고 빠른 전송 특성을 활용
- **HTTP는 연결이 필수는 아니지만 연결 기반인 TCP 표준에 의존합니다.**
  - HTTP/1.1, HTTP/2에서는 TCP를 사용한다.
  - 따라서 단순화하면 아래와 같은 구조로 볼 수 있다.
  ```text
    HTTP
    ↓
    TCP
    ↓
    IP
    ↓
    네트워크
    ```
>클라이언트와 서버가 HTTP를 요청/응답으로 교환하기 전에 여러 왕복이 필요한 프로세스인 TCP 연결을 설정해야 합니다. **HTTP/1.0의 기본 동작은 각 요청/응답에 대해 별도의 TCP 연결을 여는 것**입니다. 이 동작은 여러 요청을 연속해서 보내는 경우에는 단일 TCP 연결을 공유하는 것보다 효율적이지 못합니다.

- HTTP/1.1과 HTTP/2에서는 HTTP 통신을 하기 위해 TCP 연결을 먼저 설정한다.
    ```text
    브라우저                        서버
       │                            │
       │──── TCP 연결 설정 ─────────→│
       │                            │
       │←─── TCP 연결 완료 ──────────│
       │                            │
       │──── HTTP Request ─────────→│
       │                            │
       │←─── HTTP Response ─────────│
       │                            │
    ```
- **HTTP/1.0의 기본 동작은 각 요청/응답에 대해 별도의 TCP 연결을 여는 것입니다**
  - HTTP/1.0의 기본적인 방식에서는 아래처럼 각각 별도의 연결을 사용할 수 있었다.
    ```text
    TCP 연결
      ↓
    HTTP Request
      ↓
    HTTP Response
      ↓
    연결 종료
    
    TCP 연결
      ↓
    HTTP Request
      ↓
    HTTP Response
      ↓
    연결 종료
    
    TCP 연결
      ↓
    HTTP Request
      ↓
    HTTP Response
      ↓
    연결 종료
    ```
>이러한 결함을 개선하기 위해, HTTP/1.1은 (구현하기 어렵다고 입증된) 파이프라이닝 개념과 **지속적인 연결**의 개념을 도입했습니다: 기본적인 TCP 연결은 Connection 헤더를 사용해 부분적으로 제어할 수 있습니다. HTTP/2는 연결을 좀 더 지속되고 효율적으로 유지하는데 도움이 되도록, 단일 연결 상에서 메시지를 **다중 전송**(multiplex)하여 한 걸음 더 나아갔습니다.
- **지속적인 연결**
  - TCP 연결 하나를 여러 HTTP Request/Response에서 재사용하자.
  - 매번 TCP 연결을 새로 만들 필요가 없다.
  - HTTP/1.0 보다 훨씬 효율적이다.
    ```text
    TCP 연결 ──────────────────────────────
    
    Request 1 → Response 1
    Request 2 → Response 2
    Request 3 → Response 3
    
          ↑
    연결 재사용
    ```
- **다중 전송**
    - HTTP/2에서는 하나의 TCP 연결을 사용하면서 여러 요청/응답을 동시에 처리할 수 있다.
    - 지속적인 연결이 "하나의 연결을 여러 요청에서 재사용"하는 것이라면, 다중 전송은 "하나의 연결에서 여러 요청/응답을 동시에 처리"하는 것이다.
    ```text
    TCP 연결 ──────────────────────────────
    
    Request 1 ──────────────┐
    Request 2 ────────┐     │
    Request 3 ────────┴─────┘
                      ↓
                  동시에 처리
    ```
>HTTP에 더 알맞은 좀 더 나은 전송 프로토콜을 설계하는 실험이 진행 중에 있습니다. 예를 들어, 구글은 좀 더 신뢰성있고 효율적인 전송 프로토콜을 제공하기 위해 UDP기반의 **QUIC**를 실험하고 있습니다.
- **QUIC**
  - UDP를 기반으로 만들어진 새로운 전송 프로토콜이다.
  - HTTP/3에서 사용된다.
  - 자세한 내용은 이후 네트워크/HTTP 버전을 공부할 때 다룬다.

## HTTP로 제어할 수 있는 것
>HTTP의 확장 가능한 특성은 수년 간에 걸쳐 웹의 점점 더 많은 기능들을 제어하도록 허용되어 왔습니다. 캐시 혹은 인증 메서드는 HTTP에 초기부터 제어해왔던 기능이며, 반면에 origin 제약사항을 완화시키는 조치는 2010년에 들어서 추가되었습니다.

>다음은 HTTP 사용하여 제어 가능한 일반적인 기능 목록입니다.

> - 캐시
>   - **HTTP로 문서가 캐시되는 방식을 제어**할 수 있습니다. 서버는 캐시 대상과 기간을 프록시와 클라이언트에 지시할 수 있고 클라이언트는 저장된 문서를 무시하라고 중간 캐시 프록시에게 지시할 수 있습니다.
 
> - origin 제약사항을 완화하기
>   - 스누핑과 다른 프라이버시 침해를 막기 위해, 브라우저는 웹 사이트 간의 엄격한 분리를 강제합니다. 동일한 origin으로부터 온 페이지만이 웹 페이지의 전체 정보에 접근할 수 있죠. 그런 제약 사항은 서버에 부담이 되지만, HTTP 헤더를 통해 그것을 완화시킬 수 있습니다. 그런 덕분에 문서는 다른 도메인으로부터 전달된 정보를 패치워크할 수 있습니다(그렇게 하려면 어떤 경우에 보안과 관련된 사항이 있을 수도 있습니다).

- **Origin**: scheme + host + port의 조합
  - 브라우저가 웹사이트의 출처를 구분하는 기준
      ```text
     https://example.com:443
    
      scheme = https
      host   = example.com
      port   = 443
      ```
  - `https://bank.com` 에 로그인 후, `https://evil.com`에 접속 시 `evil.com`의 JavaScript가 아무 제한 없이 `bank.com`의 중요한 정보에 접근할 수 있다면 큰 문제가 생긴다.
  - 그래서 브라우저는 기본적으로 **서로 다른 Origin 사이의 접근을 엄격하게 제한**한다.
  - 이것이 동일 출처 정책(Same-Origin Policy)이다.
  

- 다른 Origin의 데이터가 필요한 경우
  - 프론트엔드 `https://frontend.com`, 백엔드 API `https://api.example.com` 처럼 프론트엔드와 백엔드가 서로 다른 Origin에 있을 수 있다.
  - 프론트엔드가 API 서버에 데이터를 요청해야 하지만, 브라우저의 동일 출처 정책 때문에 아무 제한 없이 접근할 수 있는 것은 아니다.
  - 서버가 HTTP 헤더를 이용해 `이 Origin에서 오는 요청은 허용해도 된다.` 라고 알려주는 방법이 있다.
  - 이것이 CORS와 연결된다
    - **CORS (Cross-Origin Resource Sharing)**
    - 브라우저의 동일 출처 정책 때문에 제한되는
      다른 Origin의 리소스 요청을 서버가 HTTP 헤더를 통해 허용할 수 있도록 하는 메커니즘이다.

> - 인증
>   - 어떤 페이지들은 보호되어 오로지 특정 사용자만이 그것에 접근할 수도 있습니다. 기본 인증은 HTTP를 통해 WWW-Authenticate 또는 유사한 헤더를 사용해 제공되거나, HTTP 쿠키를 사용해 특정 세션을 설정하여 이루어질 수도 있습니다.
- HTTP에는 인증을 위한 헤더가 있다.
    - 서버는 `WWW-Authenticate` 헤더를 통해 클라이언트에게 인증 방법 등을 알릴 수 있다.
    - 클라이언트는 `Authorization` 헤더 등을 통해 인증 정보를 전달할 수 있다.
    - 쿠키와 세션을 이용해서 로그인 상태를 유지하는 방식도 있다.

> - 프록시와 터널링
>   - 서버 혹은 클라이언트 혹은 그 둘 모두는 종종 인트라넷에 위치하며 다른 개체들에게 그들의 실제 주소를 숨기기도 합니다. HTTP 요청은 네트워크 장벽을 가로지르기 위해 프록시를 통해 나가게 되죠. **모든 프록시가 HTTP 프록시는 아닙니다**. 예를 들면 SOCKS 프로토콜은 좀 더 저수준에서 동작합니다. FTP와 같은 다른 프로토콜도 이 프록시를 통해 처리될 수 있습니다.
- **실제 주소를 숨긴다**
  - 예를 들어 회사 내부에 서버가 있는 경우
    ```text
    인터넷
       │
       ▼
    프록시
       │
       ├── 내부 서버 A
       ├── 내부 서버 B
       └── 내부 서버 C
    ```
  - 외부에서는 내부 서버의 실제 주소를 직접 알거나 접근하지 못하게 하고
  - 다음과 같은 형태로 접근하게 할 수 있다.
    ```text
    외부 사용자
         ↓
       프록시
         ↓
    내부 서버
    ```
  - 이런 식으로 네트워크 경계를 넘는 데 프록시가 사용될 수 있다.


- **모든 프록시가 HTTP 프록시는 아니다**
  - 프록시 = 중간에서 통신을 대신 전달하거나 처리하는 역할
  - HTTP 프록시는 그중 HTTP를 이해하고 처리하는 프록시
      ```text
      프록시
       ├── HTTP 관련 통신
       ├── 다른 프로토콜
       └── 기타 네트워크 통신
      ```
> - 세션
>   - **쿠키 사용은 서버 상태를 요청과 연결하도록 해줍니다**. 이것은 HTTP가 기본적으로 상태없는 프로토콜임에도 세션을 만들어주는 계기가 됩니다. 이것은 e-커머스 쇼핑 바구니를 위해서 유용할 뿐만 아니라 사용자 구성을 허용하는 모든 사이트에 대해서 유용합니다.

| 기능         | HTTP와 관계                            |
| ---------- |-------------------------------------|
| **캐시**     | HTTP Header 등을 이용해 캐시 동작 제어         |
| **Origin** | 브라우저의 출처 기반 보안 정책과 HTTP Header가 연결됨 |
| **인증**     | HTTP Header, Cookie 등을 통해 인증 정보 전달  |
| **프록시**    | HTTP 메시지를 중간에서 처리/전달                |
| **세션**     | Cookie 등을 이용해 여러 HTTP Request를 연결   |
