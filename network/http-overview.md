## HTTP 개요

> HTTP는 HTML 문서와 같은 **리소스들을 가져올 수 있도록 해주는 프로토콜**입니다.

- **프로토콜**: 서로 통신할 때 지켜야 하는 약속
    - 어떤 형식으로 메시지를 주고받을지에 대한 규칙
    - 프로그램이나 데이터 자체가 아니라, **통신을 위한 규칙**
- **리소스**: 웹에서 가져올 수 있는 대상
    - HTML, CSS, JavaScript, 이미지, 동영상, 폰트, JSON, 데이터 등

> HTTP는 웹에서 이루어지는 모든 데이터 교환의 기초이며, 클라이언트-서버 프로토콜이기도 합니다.

- **클라이언트**: 서버에게 무언가를 요청하는 쪽
    - 보통 웹 브라우저
    - Java/Spring에서는 프로그램이 다른 서버에 HTTP 요청을 보내는 경우도 볼 수 있다.

- **서버**: 클라이언트의 요청을 받아서 처리하고 응답하는 쪽

```
쇼핑몰 접속 시
[Chrome] 클라이언트
       ↓ HTTP Request
[쇼핑몰 서버] 서버
       ↓ HTTP Response
[Chrome] 클라이언트
```

- **클라이언트-서버 프로토콜**
    - 클라이언트가 요청을 시작하고 서버가 그 요청에 응답하는 구조
    - Client → Request → Server → Response → Client

> 클라이언트-서버 프로토콜이란 (보통 웹브라우저인) 수신자 측에 의해 요청이 초기화되는 프로토콜을 의미합니다. 하나의
> 완전한 문서는 텍스트, 레이아웃 설명, 이미지, 비디오, 스크립트 등 불러온(fetched) 하위 문서들로 재구성됩니다.

1. 사용자가 주소를 입력
2. 브라우저가 클라이언트 역할
3. 브라우저가 서버에게 HTTP Request를 보낸다
4. 서버가 요청을 처리한다
5. 서버가 HTTP Response를 보낸다
6. 브라우저가 받은 리소스를 이용해 웹페이지를 구성한다
    + 그리고 HTML 안에서 추가로 필요한 CSS, JavaScript, 이미지 등이 있다면 그것들을 다시 요청할 수도 있다.

> 클라이언트와 서버들은 (데이터 스트림과 대조적으로) 개별적인 메시지 교환에 의해 통신합니다. 보통 브라우저인 클라이언트에 의해 전송되는 메시지를 요청(requests)이라고 부르며, 그에 대해 서버에서 응답으로
> 전송되는 메시지를 응답(responses)이라고 부릅니다.

```
             HTTP 메시지
                  │
        ┌─────────┴─────────┐
        ↓                   ↓
     Request             Response
        ↓                   ↓
 클라이언트 → 서버      서버 → 클라이언트
 ```

- Request = 클라이언트가 서버로 보내는 HTTP 메시지
- Response = 서버가 클라이언트로 보내는 HTTP 메시지

> 1990년대 초에 설계된 HTTP는 거듭하여 진화해온 **확장 가능한** 프로토콜입니다. HTTP는 **애플리케이션 계층**의 프로토콜로, 신뢰 가능한 전송 프로토콜이라면 이론상으로는 무엇이든 사용할 수 있으나
> TCP 혹은 암호화된 TCP 연결인 TLS를 통해 전송됩니다. HTTP의 확장성 덕분에, 오늘날 하이퍼텍스트 문서 뿐만 아니라 이미지와 비디오 혹은 HTML 폼 결과와 같은 내용을 서버로 포스트(POST)하기
> 위해서도 사용됩니다. HTTP는 또한 필요할 때마다 웹 페이지를 갱신하기 위해 문서의 일부를 가져오는데 사용될 수도 있습니다.

- **확장 가능하다**: 기존의 기본 구조를 유지하면서 새로운 기능을 추가하고 발전시킬 수 있다
- **애플리케이션 계층**: 애플리케이션이 데이터를 어떤 의미와 규칙으로 주고받을지를 정의하는 계층
    - HTTP가 여기에 해당한다.
- **TLS**: HTTP 통신을 암호화하여 보호하는 기술
    - HTTPS는 HTTP에 TLS를 적용한 것이다.

**핵심**

1. HTTP는 애플리케이션 계층의 프로토콜이다.
    - 웹에서 데이터를 주고받기 위한 규칙을 정의한다.

2. HTTP가 혼자 데이터를 전달하는 것은 아니다.
    - 아래 처럼 다른 네트워크 기술과 함께 동작한다.

```
┌─────────────────┐
│      HTTP       │ ← 웹 통신 규칙
├─────────────────┤
│      TCP        │ ← HTTP 데이터를 전달하는 전송 프로토콜
├─────────────────┤
│       IP        │ ← 목적지를 찾아 전달
└─────────────────┘
```

3. HTTP는 HTML만 주고받는 기술이 아니다.
    - 아래 처럼 다양한 데이터를 주고받을 수 있다.

```
HTML
이미지
동영상
JSON
폼 데이터
```

4. HTTP는 서버에서 가져오는 것뿐만 아니라 서버로 보내는 데도 사용된다.

```
회원 가입 페이지
아이디: youngsu
비밀번호: ****

브라우저
   │
   │ POST Request
   │
   │ "회원가입 데이터를 보냅니다."
   ▼
  서버
```

## HTTP 기반 시스템의 구성요소

> HTTP는 클라이언트-서버 프로토콜입니다. 요청은 하나의 개체, **사용자 에이전트**(또는 그것을 대신하는 프록시)에 의해 전송됩니다. 대부분의 경우, 사용자 에이전트는 브라우저지만, 무엇이든 될 수 있습니다.
> 예를 들어, 검색 엔진 인덱스를 채워넣고 유지하기 위해 웹을 돌아다니는 로봇이 그러한 경우입니다.

- **사용자 에이전트(User Agent)**: 사용자를 대신해서 서버와 통신하는 프로그램
    - 대표적으로 아래와 같은 웹 브라우저
    - 사용자가 직접 HTTP 메시지를 작성하지 않아도 브라우저가 사용자의 행동을 바탕으로 HTTP Request를 만들어 서버에 보낸다.

```
Chrome
Firefox
Edge
Safari
```

```
사용자 
│  주소 입력 / 버튼 클릭 / 링크 클릭
│  
▼
브라우저
│
│ HTTP Request
▼
서버
```

- **사용자 에이전트 ≠ 브라우저**
    - 브라우저가 사용자 에이전트인 경우가 가장 흔하지만, HTTP 요청을 만들 수 있는 프로그램이라면 다른 것도 가능하다.
    - MDN에서 예로 든 게 검색 엔진 로봇이다.
- **클라이언트와 사용자 에이전트의 관계**
    - 클라이언트는 HTTP 요청을 보내는 측을 의미한다.
    - 사용자 에이전트(User Agent)는 사용자를 대신해 HTTP 요청을 보내는 프로그램을 의미한다.
    - 웹에서는 브라우저가 대표적인 사용자 에이전트이자 클라이언트이다.

> 각각의 개별적인 요청들은 서버로 보내지며, 서버는 요청을 처리하고 response라고 불리는 응답을 제공합니다. 이 요청과 응답 사이에는 여러 개체들이 있는데, 예를 들면 다양한 작업을 수행하는 게이트웨이 또는
> 캐시 역할을 하는 프록시 등이 있습니다.

- **프록시(Proxy)**: 클라이언트와 서버 사이에서 클라이언트를 대신해 HTTP 요청을 전달하는 중간 구성요소
    - 요청이나 응답을 전달하는 과정에서 캐싱, 필터링, 인증 등의 작업을 수행할 수 있다.
- **게이트웨이**: HTTP 요청을 받아서 다른 시스템이나 서비스와 연결해주는 중간 역할을 할 수 있는 구성요소

```
사용자
  │
  ▼
브라우저
(User Agent)
  │
  │ HTTP Request
  ▼
[필요한 경우]
프록시 / 캐시 / 게이트웨이 등
  │
  │ HTTP Request
  ▼
서버
  │
  │ HTTP Response
  ▼
[필요한 경우]
프록시 / 캐시 / 게이트웨이 등
  │
  │ HTTP Response
  ▼
브라우저
```

- **캐시**: 이전에 가져온 데이터를 저장해두었다가 필요할 때 다시 사용하는 것

```
서버에 매번 요청
→ 느릴 수 있음

캐시에 저장된 데이터 사용
→ 서버까지 요청하지 않아도 됨
```

**핵심**  
```HTTP 통신은 단순히 "브라우저와 서버가 직접 대화한다"가 아니라, 브라우저 같은 User Agent가 클라이언트 역할을 하여 HTTP Request를 보내고, 그 메시지가 필요에 따라 여러 중간 구성요소를 거쳐 서버에 도착한 뒤, HTTP Response가 다시 돌아오는 구조다.```

> 실제로는 브라우저와 요청을 처리하는 서버 사이에는 좀 더 많은 컴퓨터들이 존재합니다: 라우터, 모뎀 등이 있죠. 웹의 계층적인 설계 덕분에, 이들은 네트워크와 전송 계층 내로 숨겨집니다. HTTP은 애플리케이션
> 계층의 최상위에 있습니다. 네트워크 문제를 진단하는 것도 중요하지만, 기본 레이어들은 HTTP의 명세와는 거의 관련이 없습니다.

### 클라이언트: 사용자 에이전트

> 사용자 에이전트는 사용자를 대신하여 동작하는 모든 도구입니다. 이 역할은 주로 브라우저에 의해 수행됩니다; 엔지니어들과 자신들의 애플리케이션을 디버그하는 웹 개발자들이 사용하는 프로그램들은 예외입니다.

> 브라우저는 항상 요청을 보내는 개체입니다. 그것은 결코 서버가 될 수 없습니다(수년에 걸쳐 서버 초기화된 메시지를 시뮬레이션하기 위해 몇 가지 메커니즘이 추가되어 왔지만).

> 웹 페이지를 표시하기 위해, 브라우저는 페이지의 HTML 문서를 가져오기 위한 요청을 전송한 뒤, 파일을 구문 분석하여 실행해야 할 스크립트 그리고 페이지 내 포함된 하위 리소스들(보통 이미지와 비디오)을 잘
> 표시하기 위한 레이아웃 정보(CSS)에 대응하는 추가적인 요청들을 가져옵니다. 그런 뒤에 브라우저는 완전한 문서인 웹 페이지를 표시하기 위해 그런 리소스들을 혼합합니다. 브라우저에 의해 실행된 스크립트는 이후
> 단계에서 좀 더 많은 리소스들을 가져올 수 있으며 브라우저는 그에 따라 웹 페이지를 갱신하게 됩니다.

```
사용자
  │  example.com
  │ "웹사이트 열어줘"
  ▼
브라우저
  │
  │ Request
  ▼
서버
  │
  │ Response: HTML
  ▼
브라우저
  │
  ├── HTML 분석
  │
  ├── Request → CSS
  ├── Request → 이미지
  ├── Request → JavaScript
  │
  └── JavaScript 실행
          │
          └── 추가 Request → 서버
                           │
                           └── Response: JSON 등
```

> 웹 페이지는 하이퍼텍스트 문서로, 표시된 텍스트의 일부는 사용자가 사용자 에이전트를 제어하고 웹을 돌아다닐 수 있도록 새로운 웹 페이지를 가져오기 위해 실행(보통 마우스 클릭에 의해)될 수 있는 링크임을
> 뜻합니다. 브라우저는 HTTP 요청 내에서 이런 지시 사항들을 변환하고 HTTP 응답을 해석하여 사용자에게 명확한 응답을 표시합니다.

```
사용자
  │
  │ 클릭 / 주소 입력 / 버튼 클릭
  ▼
브라우저
  │
  │ HTTP Request
  ▼
서버
  │
  │ HTTP Response
  ▼
브라우저
  │
  │ 화면으로 변환
  ▼
사용자
```

**핵심**

1. 브라우저는 사용자의 행동을 계기로 HTTP Request를 만들어 서버에 보낸다.

```
사용자가 링크 클릭
        ↓
브라우저
        ↓
HTTP Request
        ↓
서버
```

2. 웹페이지 하나를 만드는 데 여러 HTTP Request가 발생할 수 있다.

```
HTML을 받은 브라우저
        ↓
HTML 분석
        ↓
필요한 CSS / JavaScript / 이미지 등을 각각 요청
        ↓
리소스를 받아 페이지 구성
        ↓
JavaScript 실행
        ↓
필요하면 추가 요청
```

- **"페이지 하나 = HTTP 요청 하나"가 아니다.**

3. 브라우저는 Response를 받아서 사람이 보는 화면으로 만든다.

```
HTTP Response
     ↓
브라우저가 해석
     ↓
HTML + CSS + JS + 이미지
     ↓
화면
```

### 웹 서버

> 통신 채널의 반대편에는 클라이언트에 의한 요청에 대한 문서를 제공하는 서버가 존재합니다. 서버는 사실 상 **논리적으로 단일 기계**입니다.이는 로드(로드 밸런싱) 혹은 그때 그때 다른 컴퓨터(캐시, DB 서버,
> e-커머스 서버 등과 같은)들의 정보를 얻고 완전하게 혹은 **부분적으로 문서를 생성**하는 소프트웨어의 복잡한 부분을 공유하는 서버들의 집합일 수도 있기 때문입니다.

- **논리적으로 단일 기계**
    - 클라이언트 입장에서는 하나의 서비스(서버)에 요청하고 응답받는 것처럼 보인다.
    - 실제로는 여러 서버와 컴퓨터가 역할을 나누어 처리할 수 있다.
    
```
                쇼핑몰 시스템
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
   웹 서버 A      웹 서버 B      웹 서버 C
       │             │             │
       └─────────────┼─────────────┘
                     ↓
                  DB 서버
```

- **부분적으로 문서를 생성**
  - ```GET /products``` 요청이 들어오면 서버가 DB에서 상품 A, B, C를 가져온 다음 필요한 데이터를 조합해서 Response를 만들어 낼 수 있다.
  - 아래는 Spring Boot 웹 애플리케이션을 예로 든 것이다.
```
상품 A
상품 B
상품 C
```
```
HTTP Request
      ↓
Spring Boot
      ↓
DB 조회
      ↓
데이터 가공
      ↓
HTTP Response
```
> 서버는 반드시 단일 머신일 필요는 없지만, 여러 개의 서버를 동일한 머신 위에서 호스팅 할 수는 있습니다. HTTP/1.1과 Host 헤더를 이용하여, 동일한 IP 주소를 공유할 수도 있습니다.
- 한 컴퓨터에서 여러 서버도 가능하고, 여러 컴퓨터가 하나의 서비스를 구성 할 수 있다.
```
컴퓨터 한 대
├── 서버 A
├── 서버 B
└── 서버 C
```
```
컴퓨터 A ─┐
컴퓨터 B ─┼→ 하나의 웹 서비스
컴퓨터 C ─┘
```
**핵심**
```서버 = 컴퓨터 한 대 라는 생각은 하면 안된다.```

### 프록시
> 웹 브라우저와 서버 사이에서는 수많은 컴퓨터와 머신이 HTTP 메시지를 이어 받고 전달합니다.
> 여러 계층으로 이루어진 웹 스택 구조에서 이러한 컴퓨터/머신들은 대부분은 **전송, 네트워크 혹은 물리 계층에서 동작하며,
> 성능에 상당히 큰 영향을 주지만 HTTP 계층에서는 이들이 어떻게 동작하는지 눈에 보이지 않습니다. 
> 이러한 컴퓨터/머신 중에서도 **애플리케이션 계층에서 동작하는 것들을 일반적으로 프록시**라고 부릅니다. 
> **프록시는 눈에 보이거나 그렇지 않을 수도 있으며**
> 다양한 기능들을 수행할 수 있습니다:
>- 캐싱 (캐시는 공개 또는 비공개가 될 수 있습니다 (예: 브라우저 캐시))  
>- 필터링 (바이러스 백신 스캔, 유해 컨텐츠 차단(자녀 보호) 기능)  
>- 로드 밸런싱 (여러 서버들이 서로 다른 요청을 처리하도록 허용)  
>- 인증 (다양한 리소스에 대한 접근 제어)  
>- 로깅 (이력 정보를 저장)  

- **애플리케이션 계층에서 HTTP 메시지를 다루는 중간 시스템을 일반적으로 프록시라고 부른다.**
  - 프록시는 HTTP를 이해하고 처리할 수 있다.
  - 따라서 단순히 데이터를 전달하는 것뿐만 아니라 HTTP 메시지를 바탕으로 다양한 작업을 수행할 수 있다.

```
브라우저
  │
  │ HTTP Request
  ▼
프록시
  │
  │ HTTP Request
  ▼
서버
  │
  │ HTTP Response
  ▼
프록시
  │
  │ HTTP Response
  ▼
브라우저
```
- **눈에 보이는 프록시 / 보이지 않는 프록시**
  - 클라이언트가 프록시의 존재를 알고 있는지 여부와 관련된 표현이다.
  - 프록시는 HTTP 메시지를 중간에서 처리하거나 필요에 따라 변경할 수 있다.
```
브라우저
   │
   │ Request A
   ▼
프록시
   │
   │ Request B
   ▼
서버
```

- **캐싱**: 데이터를 저장해두고 재사용하는 것
- **필터링**: 요청이나 응답을 검사하여 허용하거나 차단하는 것
- **로드 밸런싱**: 여러 서버에 요청을 나누어 보내는 것
- **인증**: 사용자가 누구인지 확인하는 것
- **로깅**: 요청이나 처리 결과 등의 기록을 남기는 것

**핵심**  
```라우터 등 네트워크 장비는 HTTP 자체를 처리하는 것이 아니라 주로 네트워크 계층 등의 역할을 수행한다.```  

```반면 프록시는 애플리케이션 계층에서 HTTP 메시지를 처리할 수 있기 때문에 HTTP 내용을 바탕으로 다양한 작업을 수행할 수 있다.```
```
일반적인 네트워크 장비
        ↓
HTTP보다 아래 계층에서 동작
        ↓
HTTP 내용을 직접 다루지 않음
```
```
프록시
        ↓
애플리케이션 계층에서 동작
        ↓
HTTP 메시지를 처리할 수 있음
        ↓
캐싱 / 필터링 / 로드 밸런싱 / 인증 / 로깅
```
