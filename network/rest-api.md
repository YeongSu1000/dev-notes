RESTful 웹 API 구현은 REST(Representational State Transfer) 아키텍처 원칙을 적용하여 클라이언트와 서비스 사이에 상태를 저장하지 않고, 느슨하게 결합된 인터페이스를 제공하는 웹 API입니다. RESTful 웹 API는 표준 HTTP 프로토콜을 사용하여 리소스에 대한 작업을 수행하고, 하이퍼미디어 링크와 HTTP 작업 상태 코드를 포함하는 리소스의 표현을 반환합니다.

RESTful 웹 API는 다음 원칙에 부합해야 합니다.
- **플랫폼 독립성**: **클라이언트는 내부 구현 방식과 관계없이 웹 API를 호출할 수 있음**을 의미합니다. 플랫폼 독립성을 달성하기 위해 웹 API는 HTTP를 표준 프로토콜로 사용하고, 명확한 문서를 제공하며, JSON이나 XML과 같이 익숙한 데이터 교환 형식을 지원합니다.
- **느슨한 결합**: 클라이언트와 웹 서비스가 서로 독립적으로 발전할 수 있다는 의미입니다. 클라이언트는 웹 서비스의 내부 구현 방식을 알 필요가 없으며, 웹 서비스도 클라이언트의 내부 구현 방식을 알 필요가 없습니다. RESTful 웹 API에서 느슨한 결합을 구현하려면 표준 프로토콜만 사용하고, 클라이언트와 웹 서비스가 데이터 교환 형식에 합의할 수 있도록 하는 메커니즘을 구현해야 합니다.

이 글에서는 RESTful 웹 API설계 모범 사례를 설명합니다. 또한 이해하기 쉽고, 유연하며, 유지 관리보수하기 쉬운 웹 API를 구축하기 위한 일반적인 설계 패턴과 고려 사항도 다룹니다.


## RESTful 웹 API 설계 개념
RESTful 웹 API를 구현하려면 다음 개념을 이해해야 합니다.
- URI(Uniform Resource Identifier): **REST API는 리소스를 중심으로 설계**됩니다. 리소스란 클라이언트가 접근할 수 있는 모든 종류의 객체, 데이터 또는 서비스를 의미합니다. 각 리소스는 해당 리소스를 고유하게 식별하는 URI로 표현됩니다. 예를 들어 특정 고객 주문의 URI는 다음과 같을 수 있습니다.
    ```http
    https://api.contoso.com/orders/1
    ```
- 리소스 표현은 URI로 식별되는 리소스가 XML이나 JSON과 같은 특정 형식으로 HTTP 프로토콜을 통해 어떻게 인코딩되고 전송되는지를 정의합니다. 특정 리소스를 가져오려는 클라이언트는 API에 요청을 보낼 때 해당 리소스의 URI를 사용해야 합니다. API는 URI가 가리키는 데이터의 리소스 표현을 반환합니다. 예를 들어 클라이언트는 `https://api.contoso.com/orders/1` 이라는 URI로 GET 요청을 보내 다음과 같은 JSON 본문을 받을 수 있습니다.
    ```JSON
    {"orderId":1,"orderValue":99.9,"productId":1,"quantity":1}
    ```
- 통일된 인터페이스(Uniform Interface)는 RESTful API가 클라이언트와 서비스 구현 사이에서 느슨한 결합을 달성하는 방식입니다. HTTP를 기반으로 구축된 REST API에서 통일된 인터페이스는 리소스에 대한 작업을 수행하기 위해 표준 HTTP 메서드인 `GET`, `POST`, `PUT`, `PATCH`, `DELETE`를 사용하는 것을 포함합니다.
<br><br>
- 상태 비저장 요청 모델(Stateless request model): RESTful API는 상태 비저장 요청 모델을 사용합니다. 이는 HTTP 요청이 **서로 독립적이며 어떤 순서로든 발생할 수 있다는 의미**입니다. 따라서 요청과 요청 사이에 일시적인 상태 정보를 유지하는 것은 적합하지 않습니다. 정보가 저장되는 유일한 장소는 리소스 자체이며, 각 요청은 하나의 원자적 작업이어야 합니다. 상태 비저장 요청 모델은 클라이언트와 특정 서버 사이의 연결 상태를 유지할 필요가 없기 때문에 **높은 확장성을 지원**합니다. 그러나 웹 서비스 백엔드 저장소의 확장성과 관련된 문제로 인해 상태 비저장 모델 자체가 확장성을 제한할 수도 있습니다. 데이터 저장소를 확장하는 방법에 대한 자세한 내용은 [데이터 파티셔닝](https://learn.microsoft.com/en-us/azure/architecture/best-practices/data-partitioning)을 참조하세요.
<br><br>
- 하이퍼미디어 링크: REST API는 각 리소스 표현에 포함된 하이퍼미디어 링크를 통해 동작할 수 있습니다. 예를 들어 다음 코드 블록은 주문을 JSON으로 표현한 것입니다. 이 표현에는 해당 주문과 연결된 고객을 가져오거나 업데이트할 수 있는 링크가 포함되어 있습니다.
    ```JSON
    {
      "orderID":3,
      "productID":2,
      "quantity":4,
      "orderValue":16.60,
      "links": [
        {"rel":"product","href":"https://api.contoso.com/customers/3", "action":"GET" },
        {"rel":"product","href":"https://api.contoso.com/customers/3", "action":"PUT" }
      ]
    }
    ```

## RESTful 웹 API 리소스 URI를 정의하세요
RESTful 웹 API는 리소스를 중심으로 구성됩니다. 리소스를 중심으로 API를 설계하려면 **비즈니스 엔티티**에 대응하는 리소스 URI를 정의하세요. 가능한 경우 리소스 **URI는 동사(리소스에 수행하는 작업)가 아니라 명사(리소스)를 기반**으로 만들어야 합니다.

예를 들어 전자상거래 시스템에서 주요 비즈니스 엔티티는 고객과 주문일 수 있습니다. 주문을 생성하기 위해 클라이언트는 HTTP POST 요청으로 주문 정보를 리소스 URI로 보냅니다. 요청에 대한 HTTP 응답은 주문 생성이 성공했는지를 나타냅니다.

주문 리소스를 생성하기 위한 URI는 다음과 같을 수 있습니다.
```text
https://api.contoso.com/orders // Good
```
작업을 나타내기 위해 URI에 동사를 사용하는 것은 피하세요. 예를 들어 다음 URI는 권장되지 않습니다.
```text
https://api.contoso.com/create-order // Avoid
```
엔터티는 고객이나 주문처럼 컬렉션으로 함께 그룹화되는 경우가 많습니다. 컬렉션은 컬렉션 내부의 개별 항목과는 별개의 리소스이므로 자체 URI를 가져야 합니다. 예를 들어 다음 URI는 주문 컬렉션을 나타낼 수 있습니다.
```text
https://api.contoso.com/orders
```
클라이언트는 컬렉션을 가져온 후 각 항목의 URI에 GET 요청을 보낼 수 있습니다. 예를 들어 특정 주문에 대한 정보를 받기 위해 클라이언트는 `https://api.contoso.com/orders/1` URI에 HTTP GET 요청을 보내고, 내부 주문 데이터를 리소스로 표현한 다음과 같은 JSON 본문을 받을 수 있습니다.
```JSON
{"orderId":1,"orderValue":99.9,"productId":1,"quantity":1}
```

### 리소스 URI 명명 규칙
RESTful 웹 API를 설계할 때는 리소스의 이름을 지정하고 리소스 간의 관계를 표현하는 규칙을 올바르게 사용하는 것이 중요합니다.

- **리소스 이름에는 명사를 사용한다**  
리소스를 나타낼 때는 명사를 사용합니다. 예를 들어 `/create-order` 대신 `/orders`를 사용합니다. HTTP의 GET, POST, PUT, PATCH, DELETE 메서드 자체가 이미 동작을 나타내기 때문입니다.  
<br>
- **컬렉션 URI의 이름에는 복수형 명사를 사용한다**  
일반적으로 컬렉션을 참조하는 URI에는 복수형 명사를 사용하는 것이 좋습니다. 컬렉션과 개별 항목의 URI를 계층 구조로 구성하는 것도 좋은 방법입니다.  
예를 들어 `/customers`는 고객 컬렉션의 경로이고, `/customers/5`는 ID가 5인 고객의 경로입니다. 이 방식은 웹 API를 직관적으로 이해하는 데 도움이 됩니다. 또한 많은 웹 API 프레임워크는 매개변수를 포함한 URI 경로를 기준으로 요청을 라우팅할 수 있으므로 `/customers/{id}`와 같은 경로에 대한 라우트를 정의할 수 있습니다.  
<br>
- **서로 다른 리소스 유형 간의 관계를 고려하고, 이러한 관계를 어떻게 노출할지 생각한다**  
예를 들어 `/customers/5/orders`는 고객 5의 모든 주문을 나타낼 수 있습니다.  
반대 방향으로 관계를 표현할 수도 있습니다. 즉, 주문에서 고객으로 연결하는 방식입니다. 이 경우 URI는 `/orders/99/customer`가 될 수 있습니다.  
하지만 이런 식으로 관계를 계속 확장하면 구현이 복잡해질 수 있습니다. 더 나은 방법은 HTTP 응답 메시지의 본문에 링크를 포함하는 것입니다. 그러면 클라이언트가 관련 리소스에 쉽게 접근할 수 있습니다. 이 메커니즘에 대한 자세한 내용은 [HATEOAS](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-design#implement-hateoas) 부분에서 설명합니다.  
<br>
- **리소스 간의 관계는 단순하고 유연하게 유지한다**  
복잡한 시스템에서는 클라이언트가 여러 단계의 관계를 URI를 통해 탐색할 수 있도록 `/customers/1/orders/99/products`와 같은 URI를 만들고 싶을 수 있습니다.  
하지만 이런 수준의 복잡성은 유지 관리가 어렵고, 앞으로 리소스 간의 관계가 변경될 경우 유연하지 않습니다.  
대신 URI를 비교적 단순하게 유지하도록 합니다. 애플리케이션이 어떤 리소스를 참조하게 되었다면, 그 참조를 이용해서 해당 리소스와 관련된 항목을 찾을 수 있어야 합니다.  
앞의 URI 대신 `/customers/1/orders`를 사용하여 고객 1의 모든 주문을 찾고, 그다음 `/orders/99/products`를 사용하여 해당 주문에 포함된 제품을 찾을 수 있습니다.
  > 팁  
  > collection/item/collection 보다 더 복잡한 리소스 URI를 요구하지 않도록 합니다.

- **작은 리소스를 대량으로 만들지 않는다**  
모든 웹 요청은 웹 서버에 부하를 발생시킵니다. 요청이 많아질수록 부하도 커집니다.  
작은 리소스를 대량으로 노출하는 웹 API를 수다스러운 웹 API(chatty web API)라고 합니다. 이러한 API는 클라이언트 애플리케이션이 필요한 모든 데이터를 가져오기 위해 여러 번 요청해야 하기 때문에 가급적 피하는 것이 좋습니다.  
대신 데이터를 비정규화하고 관련 정보를 더 큰 리소스로 결합하여 한 번의 요청으로 가져올 수 있도록 하는 방법을 고려할 수 있습니다.  
하지만 이 방법 역시 클라이언트가 필요로 하지 않는 데이터까지 가져오는 데 발생하는 비용과 균형을 맞춰야 합니다. 너무 큰 데이터를 가져오면 요청의 지연 시간이 증가하고 더 많은 네트워크 대역폭을 사용할 수 있습니다.
자세한 내용은 [Chatty I/O](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/chatty-io/) and [Extraneous Fetching](https://learn.microsoft.com/en-us/azure/architecture/antipatterns/extraneous-fetching/)참조  
<br>
- **데이터베이스의 내부 구조를 그대로 반영하는 API를 만들지 않는다**  
REST의 목적은 비즈니스 엔터티와 애플리케이션이 해당 엔터티에 수행할 수 있는 작업을 모델링하는 것입니다. 클라이언트에게 내부 구현을 노출해서는 안 됩니다.  
예를 들어 데이터가 관계형 데이터베이스에 저장되어 있다고 해서 웹 API가 데이터베이스의 모든 테이블을 리소스 컬렉션으로 노출할 필요는 없습니다.  
이렇게 하면 공격할 수 있는 영역이 증가하고 데이터가 유출될 수도 있습니다.  
대신 웹 API를 데이터베이스를 추상화한 계층으로 생각해야 합니다. 필요하다면 데이터베이스와 웹 API 사이에 매핑 계층을 둘 수 있습니다. 이 계층은 클라이언트 애플리케이션을 데이터베이스 스키마의 변경으로부터 분리해 줍니다.

  > 팁
  > 
  > 웹 API에서 구현하는 모든 작업을 특정 리소스에 대응시키는 것이 불가능할 수도 있습니다  
  > 이러한 비리소스 상황은 함수를 호출하는 HTTP 요청을 사용하고, 그 결과를 HTTP 응답 메시지로 반환하는 방식으로 처리할 수 있습니다.
  >
  > 예를 들어 덧셈과 뺄셈 같은 간단한 계산 기능을 제공하는 웹 API가 있다고 합시다. 이러한 작업을 가상의 리소스처럼 보이는 URI로 노출하고, 필요한 매개변수는 쿼리 문자열을 사용하여 지정할 수 있습니다.  
  > `/add?operand1=99&operand2=1` URI로 GET 요청을 보내면 응답 메시지의 본문에 값 100이 포함되어 반환됩니다.
  >
  > 하지만 이러한 형태의 URI는 꼭 필요한 경우에만 제한적으로 사용해야 합니다.

## RESTful 웹 API 메서드를 정의합니다.
RESTful 웹 API 메서드는 HTTP 프로토콜에서 정의한 요청 메서드 및 미디어 유형과 일치해야 합니다. 이 섹션에서는 RESTful 웹 API에서 가장 일반적으로 사용되는 요청 메서드와 미디어 유형에 대해 설명합니다.

### HTTP 요청 메서드
HTTP 프로토콜은 리소스에 수행하려는 작업을 나타내는 다양한 요청 메서드를 정의합니다. RESTful 웹 API에서 가장 일반적으로 사용되는 메서드는 GET, POST, PUT, PATCH, DELETE​입니다. 각각의 메서드는 특정 작업에 대응합니다. RESTful 웹 API를 설계할 때는 프로토콜의 정의, 접근하려는 리소스, 수행하려는 작업에 일관되도록 이러한 메서드를 사용해야 합니다.    

특정 요청 메서드의 동작은 해당 리소스가 컬렉션인지 개별 항목인지에 따라 달라질 수 있다는 점을 기억하는 것이 중요합니다. 다음 표는 대부분의 RESTful 구현에서 사용하는 몇 가지 일반적인 규칙을 보여줍니다.

> 중요  
> 다음 표에서는 전자 상거래의 `customer` 엔터티를 예제로 사용합니다. 웹 API가 모든 요청 메서드를 구현할 필요는 없습니다. 어떤 메서드를 구현할지는 구체적인 상황에 따라 달라집니다.

| 리소스            | POST      | GET | PUT | DELETE     |
|----------------|-----------|-----|-----|------------|
| `/customers`   | 새로운 고객 생성 |모든 고객 조회| 고객 일괄 수정| 모든 고객 삭제   |
| `/customers/1` | 오류        |고객 1의 상세 정보 조회|고객 1이 존재한다면 해당 고객의 상세 정보 수정| 고객 1 삭제 |
|`/customers/1/orders`|고객 1의 새로운 주문 생성|고객 1의 모든 주문 조회|고객 1의 주문 일괄 수정|고객 1의 모든 주문 삭제|

### GET 요청
GET 요청은 지정된 URI에 있는 리소스의 표현을 가져옵니다. 응답 메시지의 본문에는 요청한 리소스의 세부 정보가 포함됩니다.  

GET 요청은 다음 HTTP 상태 코드 중 하나를 반환해야 합니다.  

|HTTP 상태 코드|이유|
|---|---|
|200 (OK)|메서드가 리소스를 성공적으로 반환했습니다.|
|204 (No Content)|응답 본문에 내용이 없습니다. 예를 들어 검색 요청의 결과가 없을 때 사용할 수 있습니다.|
|404 (Not Found)|요청한 리소스를 찾을 수 없습니다.|

### POST 요청
POST 요청은 리소스를 생성해야 합니다. 서버는 새 리소스에 대한 URI를 할당하고 해당 URI를 클라이언트에 반환합니다.  
> 중요  
> POST 요청에서 클라이언트는 자체적으로 URI를 생성하려고 해서는 안 됩니다. 클라이언트는 컬렉션의 URI로 요청을 보내야 하며, 서버가 새로운 리소스에 URI를 할당해야 합니다.
> 클라이언트가 자체적으로 URI를 생성하고 특정 URI에 POST 요청을 보내려고 하면, 서버는 해당 메서드가 지원되지 않음을 나타내기 위해 HTTP 상태 코드 400 (Bad Request)​을 반환합니다.

RESTful 모델에서 POST 요청은 URI가 식별하는 컬렉션에 새로운 리소스를 추가하는 데 사용됩니다. 그러나 POST 요청은 새로운 리소스를 생성하지 않고 기존 리소스에 데이터를 전달하여 처리를 요청하는 데 사용할 수도 있습니다.  

POST 요청은 다음 HTTP 상태 코드 중 하나를 반환해야 합니다.  

|HTTP 상태 코드|이유|
|---|---|
|200 (OK)|메서드가 어떤 처리를 수행했지만 새로운 리소스를 생성하지 않았습니다. 작업의 결과가 응답 본문에 포함될 수 있습니다.|
|201 (Created)|리소스가 성공적으로 생성되었습니다. 새 리소스의 URI는 응답의 Location 헤더에 포함됩니다. 응답 본문에는 해당 리소스의 표현이 포함됩니다.|
|204 (No Content)|응답 본문에 내용이 없습니다.|
|400 (Bad Request)|클라이언트가 요청에 잘못된 데이터를 포함했습니다. 응답 본문에는 오류에 대한 추가 정보나 더 자세한 내용을 제공하는 URI 링크가 포함될 수 있습니다.|
|405 (Method Not Allowed)|클라이언트가 POST 요청을 지원하지 않는 URI에 POST 요청을 보내려고 했습니다.|

### PUT 요청
PUT 요청은 기존 리소스가 존재한다면 해당 리소스를 업데이트하고, 존재하지 않는다면 경우에 따라 새로운 리소스를 생성해야 합니다.
PUT 요청을 수행하는 과정은 다음과 같습니다.

1. 클라이언트는 리소스의 URI를 지정하고, 리소스의 전체 표현을 포함하는 요청 본문을 함께 보냅니다.
2. 클라이언트가 요청을 보냅니다.
3. 해당 URI를 가진 리소스가 이미 존재한다면 해당 리소스가 대체됩니다. 그렇지 않으면 해당 경로가 이를 지원하는 경우 새로운 리소스가 생성됩니다.

PUT 메서드는 컬렉션보다는 특정 고객과 같은 개별 리소스에 적용됩니다.
서버는 PUT을 통한 업데이트는 지원하지만 PUT을 통한 생성은 지원하지 않을 수도 있습니다. PUT을 통한 생성을 지원할지는 리소스가 존재하기 전에 클라이언트가 해당 리소스에 대한 URI를 의미 있고 신뢰성 있게 지정할 수 있는지에 따라 결정됩니다.
클라이언트가 URI를 지정할 수 없다면 POST를 사용하여 리소스를 생성하고 서버가 URI를 할당하도록 해야 합니다. 그런 다음 해당 URI의 리소스를 업데이트할 때 PUT 또는 PATCH를 사용합니다.

> 중요  
> PUT 요청은 멱등적(idempotent)이어야 합니다. 즉, 동일한 요청을 여러 번 제출하더라도 항상 동일한 리소스가 동일한 값으로 수정되어야 합니다.
> 클라이언트가 PUT 요청을 다시 보내더라도 결과는 변경되지 않아야 합니다. 
> 반면 POST와 PATCH 요청은 멱등적이라는 보장이 없습니다.

PUT 요청은 다음 HTTP 상태 코드 중 하나를 반환해야 합니다.  

| HTTP 상태 코드 | 이유 |
|---|---|
|200 (OK)|리소스가 성공적으로 업데이트되었습니다.|
|201 (Created)|리소스가 성공적으로 생성되었습니다. 응답 본문에 해당 리소스의 표현이 포함될 수 있습니다.|
|204 (No Content)|리소스가 성공적으로 업데이트되었지만 응답 본문에는 내용이 없습니다.|
|409 (Conflict)|리소스의 현재 상태와 충돌하여 요청을 완료할 수 없습니다.|

> 팁  
> 여러 리소스에 대한 업데이트를 하나의 요청으로 묶을 수 있도록 일괄 HTTP PUT 작업을 구현하는 것을 고려해 보세요. PUT 요청에서는 컬렉션의 URI를 지정해야 합니다. 요청 본문에는 수정할 리소스들의 세부 정보가 포함되어야 합니다. 이 방법은 요청 횟수를 줄이고 성능을 향상시키는 데 도움이 될 수 있습니다.

### PATCH 요청
PATCH 요청은 기존 리소스의 일부를 수정합니다. 클라이언트는 리소스의 URI를 지정합니다. 요청 본문에는 리소스에 적용할 변경 사항이 포함됩니다.  
PATCH는 클라이언트가 리소스 전체를 보내는 것이 아니라 변경 사항만 보내기 때문에 PUT 요청보다 효율적일 수 있습니다.  
서버가 해당 동작을 지원하는 경우, PATCH는 비어 있거나 null인 리소스에 일련의 변경 사항을 적용하여 새로운 리소스를 생성하는 데 사용될 수도 있습니다.  

PATCH 요청에서 클라이언트는 패치 문서(patch document) 형태로 기존 리소스에 적용할 변경 사항을 보냅니다. 서버는 이 패치 문서를 처리하여 리소스를 수정합니다.  
패치 문서는 전체 리소스를 설명하는 것이 아니라 적용할 변경 사항만 지정합니다.  
PATCH 메서드에 대한 명세인 [RFC 5789](https://datatracker.ietf.org/doc/html/rfc5789)에서는 패치 문서에 사용할 특정 형식을 정의하지 않습니다. 어떤 형식을 사용할지는 요청에 포함된 미디어 유형을 통해 판단해야 합니다.  

JSON은 웹 API에서 가장 일반적으로 사용되는 데이터 형식 중 하나입니다. JSON을 기반으로 하는 대표적인 두 가지 패치 형식은 JSON Patch와 JSON Merge Patch입니다.  

JSON Merge Patch는 JSON Patch보다 단순합니다. 패치 문서는 원래 JSON 리소스와 동일한 구조를 가지지만, 변경하거나 추가해야 하는 필드만 포함합니다.  
또한 패치 문서에서 필드의 값을 null로 지정하면 해당 필드를 삭제할 수 있습니다.  
이러한 의미 때문에 원래 리소스에서 명시적인 null 값을 가질 수 있는 경우에는 Merge Patch를 사용하기에 적합하지 않습니다.  

예를 들어 원래 리소스가 다음과 같은 JSON 표현을 가지고 있다고 가정해 보겠습니다.
```JSON
{
    "name":"gizmo",
    "category":"widgets",
    "color":"blue",
    "price":10
}
```
이 리소스에 적용할 수 있는 JSON Merge Patch는 다음과 같습니다.
```JSON
{
    "price":12,
    "color":null,
    "size":"small"
}
```
이 Merge Patch는 서버에 다음과 같은 변경을 수행하도록 지시합니다.
- `price`를 12로 변경
- `color`를 삭제
- `size`를 추가  
`name`과 `category`의 값은 변경되지 않습니다.  

JSON Merge Patch에 대한 자세한 내용은 [RFC 7396](https://datatracker.ietf.org/doc/html/rfc7396)을 참고할 수 있습니다. JSON Merge Patch의 미디어 유형은 `application/merge-patch+json`입니다.  

원래 리소스가 명시적인 null 값을 가질 수 있는 경우에는 Merge Patch를 사용하기에 적합하지 않습니다. 이는 패치 문서에서 null이 특별한 의미를 가지기 때문입니다.  
또한 패치 문서는 서버가 변경 사항을 적용해야 하는 순서를 지정하지 않습니다. 이 순서가 중요한지는 데이터와 해당 도메인에 따라 달라집니다.  

[RFC 6902](https://datatracker.ietf.org/doc/html/rfc6902)에서 정의한 JSON Patch는 적용할 작업을 순서대로 지정하기 때문에 더 유연합니다. JSON Patch에서는 add, remove, replace, copy, test 등의 작업을 지정하여 값을 검증할 수도 있습니다.  

JSON Patch의 미디어 유형은 application/json-patch+json입니다.  

PATCH 요청은 다음 HTTP 상태 코드 중 하나를 반환해야 합니다.  

|HTTP 상태 코드|이유|
|---|---|
|200 (OK)|리소스가 성공적으로 수정되었습니다.|
|400 (Bad Request)|패치 문서의 형식이 잘못되었습니다.|
|409 (Conflict)|패치 문서는 유효하지만 리소스의 현재 상태에서는 변경 사항을 적용할 수 없습니다.|
|415 (Unsupported Media Type)|패치 문서의 형식을 지원하지 않습니다.|

### DELETE 요청
DELETE 요청은 지정된 URI에 있는 리소스를 삭제합니다.  
DELETE 요청은 다음 HTTP 상태 코드 중 하나를 반환해야 합니다.

|HTTP 상태 코드|이유|
|---|---|
|204 (No Content)|리소스가 성공적으로 삭제되었습니다. 작업이 성공적으로 처리되었으며 응답 본문에는 추가 정보가 없습니다.|
|404 (Not Found)|해당 리소스가 존재하지 않습니다.|

### 리소스의 MIME 타입
리소스 표현(resource representation)이란 URI로 식별되는 리소스를 특정 형식(예: XML 또는 JSON)으로 인코딩하고 HTTP 프로토콜을 통해 전송하는 방식을 말합니다. 특정 리소스를 가져오려는 클라이언트는 API 요청에 해당 리소스의 URI를 사용해야 합니다. API는 URI가 가리키는 데이터의 리소스 표현을 반환하는 방식으로 응답합니다.  

HTTP 프로토콜에서는 리소스 표현 형식을 미디어 타입(media type)을 사용하여 지정합니다. 미디어 타입은 MIME 타입이라고도 합니다. 바이너리가 아닌 데이터의 경우 대부분의 웹 API는 JSON(application/json)을 지원하며, XML(application/xml)도 지원할 수 있습니다.  

요청 또는 응답의 Content-Type 헤더는 리소스 표현의 형식을 지정합니다. 다음 예시는 JSON 데이터를 포함하는 POST 요청을 보여줍니다.
```HTTP
POST https://api.contoso.com/orders
Content-Type: application/json; charset=utf-8
Content-Length: 57

{"Id":1,"Name":"Gizmo","Category":"Widgets","Price":1.99}
```
서버가 해당 미디어 타입을 지원하지 않는 경우 HTTP 상태 코드 415 (Unsupported Media Type)을 반환해야 합니다.  
클라이언트의 요청에는 Accept 헤더를 포함할 수도 있습니다. Accept 헤더에는 클라이언트가 서버의 응답 메시지에서 받아들일 수 있는 미디어 타입 목록이 포함됩니다.  
예를 들어:
```HTTP
GET https://api.contoso.com/orders/2
Accept: application/json, application/xml
```
서버가 목록에 있는 미디어 타입 중 어느 것도 사용할 수 없다면 HTTP 상태 코드 406 (Not Acceptable)을 반환해야 합니다.

## 비동기 메서드를 구현하세요
때때로 POST, PUT, PATCH, DELETE 메서드는 완료하는 데 시간이 오래 걸리는 처리를 필요로 할 수 있습니다. 처리가 완료될 때까지 기다린 후 클라이언트에 응답을 보내면, 허용하기 어려울 정도로 긴 지연 시간이 발생할 수 있습니다. 이런 상황에서는 해당 메서드를 비동기 방식으로 만드는 것을 고려해야 합니다.  
비동기 메서드는 HTTP 상태 코드 202 (Accepted) 를 반환하여, 요청이 처리를 위해 받아들여졌지만 아직 처리가 완료되지 않았음을 나타내야 합니다.  

클라이언트가 상태 엔드포인트를 주기적으로 조회하여 비동기 요청의 상태를 확인할 수 있도록, 비동기 요청의 상태를 반환하는 엔드포인트를 제공합니다. 202 응답의 Location 헤더에 상태 엔드포인트의 URI를 포함합니다.  
예를 들어:
```HTTP
HTTP/1.1 202 Accepted
Location: /api/status/12345
```
클라이언트가 이 엔드포인트에 GET 요청을 보내면, 응답에는 해당 요청의 현재 상태가 포함되어야 합니다. 선택적으로 완료까지 예상되는 시간이나 작업을 취소할 수 있는 링크를 포함할 수도 있습니다.
```HTTP
HTTP/1.1 200 OK
Content-Type: application/json

{
    "status":"In progress",
    "link": { "rel":"cancel", "method":"delete", "href":"/api/status/12345" }
}
```
비동기 작업이 새로운 리소스를 생성한다면, 작업이 완료된 후 상태 엔드포인트는 303 (See Other) 상태 코드를 반환해야 합니다. 303 응답에는 새 리소스의 URI를 제공하는 Location 헤더를 포함합니다.
```HTTP
HTTP/1.1 303 See Other
Location: /api/orders/12345
```
더 자세한 내용은 [장시간 실행되는 요청에 대한 비동기 지원 제공](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-implementation#provide-asynchronous-support-for-long-running-requests) 및 [비동기 요청-응답 패턴](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply)을 참고하세요.




## 데이터 페이지네이션 및 필터링 기능을 구현하세요.
데이터 조회를 최적화하고 응답 데이터의 크기를 줄이려면, API 설계에 데이터 페이지네이션과 쿼리 기반 필터링을 구현하세요. 이러한 기법을 사용하면 클라이언트가 필요한 데이터의 일부만 요청할 수 있으므로 성능을 향상시키고 네트워크 대역폭 사용량을 줄일 수 있습니다.
- **페이지네이션**(Pagination)은 대규모 데이터 집합을 더 작고 관리하기 쉬운 단위로 나눕니다. 반환할 항목의 개수를 지정하려면 `limit`과 같은 쿼리 매개변수를 사용하고, 데이터의 시작 지점을 지정하려면 `offset`을 사용하세요. 또한 `limit`과 `offset`에 의미 있는 기본값을 제공해야 합니다. 예를 들어 `limit=25, offset=0`과 같이 설정할 수 있습니다.
```HTTP
GET /orders?limit=25&offset=50
```
  - `limit`: 반환할 항목의 최대 개수를 지정합니다.
  - `offset`: 데이터의 시작 인덱스를 지정합니다.
> 팁  
> 서비스 거부 공격(DoS 공격)을 방지하는 데 도움이 되도록, 반환되는 항목 수에 상한을 설정하는 것을 고려하세요. 예를 들어 서비스가 `max-limit=25`를 설정하고 있는데 클라이언트가 `limit=1000`을 요청한다면, API 문서의 정책에 따라 서비스는 25개의 항목만 반환하거나 HTTP BAD REQUEST 오류를 반환할 수 있습니다.
- **필터링**(Filtering)을 사용하면 클라이언트가 조건을 적용하여 데이터 집합을 원하는 범위로 좁힐 수 있습니다. API는 클라이언트가 URI의 쿼리 문자열에 필터 조건을 전달하도록 허용할 수 있습니다.
```HTTP
GET /orders?minCost=100&status=shipped
```
  - `minCost`: 최소 비용이 100인 주문으로 필터링합니다.
  - `status`: 특정 상태를 가진 주문으로 필터링합니다.

다음과 같은 모범 사례를 고려하세요.
- **정렬**(Sorting)을 사용하면 클라이언트가 `sort` 매개변수를 사용하여 데이터를 정렬할 수 있습니다. 예를 들어 `sort=price`와 같이 사용할 수 있습니다.
> 중요  
> 정렬 방식은 캐싱에 부정적인 영향을 줄 수 있습니다. 쿼리 문자열 매개변수는 많은 캐시 구현에서 캐시된 데이터의 키로 사용하는 리소스 식별자의 일부를 구성하기 때문입니다.
- **클라이언트가 정의하는 프로젝션을 위한 필드 선택**(Field selection for client-defined projections)을 사용하면 클라이언트가 `fields` 매개변수를 이용하여 자신에게 필요한 필드만 지정할 수 있습니다. 예를 들어 `fields=id,name`과 같이 사용할 수 있습니다. 또한 */orders?fields=ProductID,Quantity*처럼 쉼표로 구분된 필드 목록을 받는 쿼리 문자열 매개변수를 사용할 수도 있습니다.

API는 클라이언트가 요청한 필드를 검증해야 합니다. 이를 통해 클라이언트가 해당 필드에 접근할 권한이 있는지 확인하고, API를 통해 일반적으로 제공하지 않는 필드가 노출되는 것을 방지해야 합니다.

## 부분 응답을 지원합니다.

일부 리소스에는 파일이나 이미지처럼 용량이 큰 바이너리 필드가 포함되어 있습니다. 불안정하고 간헐적으로 연결이 끊기는 상황에서 발생하는 문제를 해결하고 응답 시간을 개선하려면, 용량이 큰 바이너리 리소스를 부분적으로 가져오는 기능을 지원하는 것을 고려하세요.  

부분 응답을 지원하려면 웹 API는 용량이 큰 리소스에 대한 GET 요청에서 Accept-Ranges 헤더를 지원해야 합니다. 이 헤더는 해당 GET 작업이 부분 요청을 지원한다는 것을 나타냅니다. 클라이언트 애플리케이션은 바이트 범위로 지정된 리소스의 일부만 반환하도록 GET 요청을 보낼 수 있습니다.  

또한 이러한 리소스에 대해 HTTP HEAD 요청을 구현하는 것도 고려하세요. HEAD 요청은 리소스를 설명하는 HTTP 헤더만 반환하고 메시지 본문은 비워 둔다는 점을 제외하면 GET 요청과 유사합니다. 클라이언트 애플리케이션은 HEAD 요청을 사용하여 부분적인 GET 요청으로 리소스를 가져올 필요가 있는지 판단할 수 있습니다.  
예:
```HTTP
HEAD https://api.contoso.com/products/10?fields=productImage
```
다음은 응답 메시지의 예시입니다.
```HTTP
HTTP/1.1 200 OK

Accept-Ranges: bytes
Content-Type: image/jpeg
Content-Length: 4580
```
Content-Length 헤더는 리소스 전체의 크기를 나타내며, Accept-Ranges 헤더는 해당 리소스에 대한 GET 작업이 부분적인 결과를 지원한다는 것을 나타냅니다. 클라이언트 애플리케이션은 이 정보를 사용하여 이미지를 더 작은 단위로 나누어 가져올 수 있습니다.  
첫 번째 요청은 Range 헤더를 사용하여 처음 2,500바이트를 가져옵니다.
```HTTP
GET https://api.contoso.com/products/10?fields=productImage
Range: bytes=0-2499
```
응답 메시지는 HTTP 상태 코드 206을 반환하여 이 응답이 부분 응답임을 나타냅니다. Content-Length 헤더는 리소스 전체 크기가 아니라 메시지 본문에 실제로 반환된 바이트 수를 나타냅니다. Content-Range 헤더는 리소스에서 어떤 부분이 반환되었는지를 나타냅니다. 즉, 전체 4,580바이트 중 0~2,499바이트가 반환되었다는 뜻입니다.
```HTTP
HTTP/1.1 206 Partial Content

Accept-Ranges: bytes
Content-Type: image/jpeg
Content-Length: 2500
Content-Range: bytes 0-2499/4580

[...]
```
그다음 클라이언트 애플리케이션은 추가 요청을 보내 리소스의 나머지 부분을 가져올 수 있습니다.
